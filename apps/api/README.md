# @libras/api

The LIBRAS API: Node.js, Express and TypeScript, backed by Supabase PostgreSQL (ADR 0003). The mobile app and the Librarian pages talk only to this API.

How to run it and its tests is in the [root README](../../README.md).

## Layout

| Path | Contents |
| --- | --- |
| `src/server.ts` | The entry point: reads configuration, wires the real clock, database and email sender, and listens |
| `src/app.ts` | `createApp(deps)` builds the Express app (`{ app, stop }`: call `stop` when the server closes). Each feature adds its router here |
| `src/routes/` | One router per feature. `health.ts` is the pattern to copy |
| `src/errors.ts` | `AppError` and the error handler |
| `src/clock.ts`, `src/email.ts`, `src/db.ts`, `src/logger.ts` | The things the API reaches outside itself, passed in as `AppDeps` (also `files`, the Storage of Announcement posters) |
| `src/members/` | Member profiles, the sign-up flow (pending sign-up, emailed code, activation) |
| `src/auth/` | Sign-in sessions, guards (`requireLibrarian`, `requireMember`), identity pass-through to PostgreSQL |
| `src/audit/` | The append-only, hash-chained audit log: `record`, `verify`, the event whitelist |
| `src/holds/` | Holds: `placeHold`, `listHolds`, `cancelHold`, the priority weights (`priority.ts`) and Hold dispatch (`dispatch.ts`: `dispatchCopy`, `announceDispatch`) |
| `src/copies/` | `lockCopy(tx, { code } or { id })`: the one query that locks a Copy (by what the desk scanned, or by id), and `CopyRow` |
| `src/loans/` | Loans: `confirmLoan` and `recordReturn` (the desk), `listLoans` (My Loans, `my-loans.ts`) and `renewLoan` (`renewals.ts`, with the rules in `renewability.ts`) |
| `src/standing/` | Clearance and Good standing (ADR 0010): `readStanding` (a Member's Loans still out and unsettled Fines), `clearanceOf` and `goodStandingOf` (the one place that says what each is), `goodStandingRefusal` and `requireGoodStanding` (the refusals of a Loan, a Hold and a Renewal) |
| `src/fines/` | Fines (ADR 0010): `fineAt` (the amount at a moment, the one place that computes it), `fixFine` (stores it at a return) and `settleFine` (a Librarian settles it as paid or waived) |
| `src/announcements/` | Announcements for Librarians: the service (`index.ts`: list, create, edit, end now, delete, and `runningAnnouncement` for Home), the poster images (`images.ts`, sharp) and the file store (`storage.ts`: `FileStore`, `SupabaseFileStore`, `announcementFiles`) |
| `src/sweep.ts` | The sweep tick: `runSweep` (Pickup Window expiry, then Loan notices; one failing job does not stop the other) and `startSweeper` (the 60-second timer) |
| `src/notices/` | Loan notices: when each is due (`schedule.ts`), the email (`email.ts`) and the job (`index.ts`, `sendLoanNotices`) |
| `src/scanner/` | The phone as the scanner: `ScannerHub` (pairing codes, scanner tokens, the desk streams), see "The phone scanner" |
| `src/catalog/` | `CatalogSearch`: the in-memory search index, its rebuild-and-swap, and live availability |
| `src/seed/` | `npm run seed`: the Librarian, the Loan Policy rows and the Pickup Window setting (`circulation.ts`: puts back missing rows, keeps existing values), and the sample catalog (`catalog-generator.ts` is pure and reproducible, `catalog.ts` writes it) |
| `src/testing/` | The HTTP test harness, also exported as `@libras/api/testing`, and the end-to-end server `e2e-server.ts` |
| `test/` | Tests, `*.test.ts`, run with Node's built-in test runner |

## Hosted configuration

In production (`NODE_ENV=production`, as on Render) the API refuses to start without `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `BREVO_API_KEY` and `EMAIL_FROM_ADDRESS`, and sends email through `BrevoEmailSender`. Elsewhere, with those two Brevo settings unset, email is printed to the console. `TRUST_PROXY` (number of reverse proxies in front of the API, `1` on Render, default 0) sets Express `trust proxy` so the sign-in limiter sees the real client address. `CORS_ALLOWED_ORIGINS` (exact origins, comma separated) lets hosted web pages call the API; the default is none. `SWEEP_SECRET` (at least 32 characters, optional) mounts `POST /internal/sweeps/pickup-expiry`, which the database schedule calls to end Pickup Windows while the service sleeps (see Pickup Window expiry); production logs a warning at start without it. `scripts/` holds the hosted commands (`migrate-hosted.ts`, `check-hosted.ts`, `send-test-email.ts`, `schedule-pickup-sweep.ts`); see the Deployment section of the root README.

## Rules for new code

- **Time.** Never call `new Date()` or `Date.now()` for business logic, and never use SQL `now()` for it. Take the time from `deps.clock.now()` and pass it to PostgreSQL as a query parameter. Otherwise tests cannot move time.
- **Email.** Send only through `deps.email.send(...)`.
- **Errors.** To refuse a request, `throw new AppError(status, code, message)`. The `code` is stable snake_case for programs, and the `message` is shown to a Member or Librarian, so it says what they can do next. Anything else that is thrown becomes a 500 with code `internal_error` and a generic message. The detail is logged on the server and never returned. Every error response has the shape `{ "error": { "code": "...", "message": "..." } }` (`ApiErrorBody` in `@libras/shared`).
- **Async handlers.** Express 5 forwards a rejected promise to the error handler, so no `try`/`catch` wrapper or `next(error)` is needed.
- **Imports.** There is no build step: Node runs the TypeScript directly. Relative imports need the `.ts` extension, type imports need `import type`, and syntax that needs compiling (enums, namespaces, parameter properties) is not allowed.

## Writing an API test

```ts
import assert from "node:assert/strict";
import { after, before, describe, it } from "node:test";
import { startTestApi } from "../src/testing/index.ts";
import type { TestApi } from "../src/testing/index.ts";

describe("Hold ready email", () => {
  let api: TestApi;
  before(async () => {
    api = await startTestApi();
  });
  after(() => api.close());

  it("is sent when a Copy is returned", async () => {
    api.clock.set("2026-11-24T08:00:00.000Z"); // the API now runs at this time
    api.clock.advance({ hours: 24, seconds: 1 }); // and stands still until moved again

    const response = await fetch(`${api.baseUrl}/health`); // real HTTP

    assert.equal(response.status, 200);
    assert.equal(api.emails.sent.length, 0); // every email the API sent
    assert.equal(api.emails.lastTo("ana.reyes@umak.edu.ph"), undefined);
  });
});
```

- `api.baseUrl` is where to send requests. Tests observe behaviour through HTTP.
- `api.clock` is a `FakeClock`: `set(dateOrIsoString)`, `advance({ days, hours, minutes, seconds, milliseconds })`, `now()`. It starts at the real time and stands still.
- `api.emails` is a `CapturingEmailSender`: `sent`, `lastTo(address)`, `clear()`.
- `api.db` is the API's `pg` pool on the real local PostgreSQL, for arranging data that has no endpoint yet.
- `startTestApi({ extraRoutes })` mounts test-only routes, for example one that throws. `startTestApi({ databaseUrl })` points the API at another database.
- `startTestApi({ trustProxy: 1, signInLimit: { maxFailures, windowMinutes } })`: with `trustProxy: 1` a test gives each request a client address of its own through `X-Forwarded-For` (without it every test request is 127.0.0.1); `signInLimit` lowers the sign-in limit so a test needs fewer failures (each one reaches Supabase Auth, which has its own limit).
- Test files run one at a time (`--test-concurrency=1`) because they share one database.

## Test helpers for Members

```ts
import { createTestMember, studentSignUpBody, codeFromEmail, signInDirect } from "@libras/api/testing";

const ana = await createTestMember(api, { firstName: "Ana" }); // signs up, reads the emailed code, verifies, signs in
ana.member;      // MemberProfile
ana.accessToken; // Authorization: Bearer <accessToken>
```

`studentSignUpBody()` is a valid UMAK Student sign-up with a unique email, username and student number; `facultySignUpBody()`, `ntpEmployeeSignUpBody()`, `visitorSignUpBody()` and `alumniSignUpBody()` do the same for the other Account Types. `codeFromEmail(api.emails.lastTo(email))` reads the verification code. `startTestApi({ wrapAccounts })` wraps the real Supabase account administration, for a test that makes one of its calls fail.

`src/db.ts` also holds what transactions share: the `Tx` type, `isUniqueViolation(error, constraint)` (a unique index refusing a row, by its name), and `retryOnConflict`, which runs an attempt again when it ends in a conflict (a Loan meeting a Pickup Window that has ended, a return whose Copy changed hands, a cancel whose Hold was dispatched meanwhile).

Finishing a sign-up (`verifySignUp`) calls nothing outside the database inside a transaction: one transaction checks the code and creates the Member (keeping the pending sign-up), then Supabase Auth confirms the email, then the pending sign-up is deleted. A failure after the first step leaves a Member who cannot sign in yet; the answer is `503 sign_up_unfinished` and entering the same code again finishes it. A confirmed email therefore always has its Member. `createTestAccount(api)` makes a bare Supabase account (no Member profile) and, with `{ staff }`, a Librarian.

## Member sign-in and who may call a route

`POST /members/sign-in` (`members/sign-in.ts`, `signInMember`) is the one place a Member session starts. A route that needs a Member is `router.get(path, ...requireMember(deps), (_req, res) => { memberOf(res) })`; any signed-in person is `requireIdentity(deps)`; a Librarian is `...requireLibrarian(deps)`. Sessions are renewed at `POST /auth/refresh` and ended at `POST /auth/sign-out`. `AttemptLimiter` (`auth/attempt-limit.ts`) blocks a client address after repeated refusals; both sign-in routes and the scanner pairing route go through it. Each attempt reserves its failure before it runs and gives it back unless it ends in a 401 or 403, so parallel guesses cannot pass the limit together. Its state is in memory by decision (ticket #9): one instance, and a restart forgets it. Details for later tickets: the spec2-notes `ticket-9.md` (outside the repository) and the README, "Client address and the sign-in limit".

## Forgot password

`members/password-reset.ts`, routes in `routes/password-reset.ts`, table `public.password_resets` (migration `..._password_resets.sql`). Members only: a Librarian's email is treated like an unknown one.

- `POST /members/password-reset` `{ email }` -> `200 { email, codeExpiresAt }` for every email. A Member's email gets a code (`passwordResetCodeEmail`, same 6 digits, 10 minute life and 5 wrong guesses as sign-up, `members/verification-code.ts`); any other email gets a row with no code and no email, so the wrong-guess count, the expiry and every answer about it are the same. The email is sent without waiting, so the reply time does not depend on the account either. A new request replaces the code and resets that code's count of wrong guesses. `429 too_many_attempts` (Retry-After) past the limits: `DEFAULT_PASSWORD_RESET_LIMIT` (`members/password-reset.ts`) is 10 requests per 15 minutes per client address and 5 per hour per email. The per-address limit is in memory (`RequestLimiter`, `auth/request-limit.ts`, which counts every request; `AttemptLimiter` counts only refusals): it only slows one address that floods many inboxes, and a restart of the API gives that address one fresh start. The per-email limit is in the database (table `public.password_reset_attempts`, migration `..._password_reset_attempts.sql`), so the free host's restarts do not reset it. `startTestApi({ passwordResetLimit })` sets them.
- `POST /members/password-reset/check` `{ email, code }` -> `204`, or `400 invalid_code`, `400 code_expired`, `429 too_many_attempts` (`PASSWORD_RESET_MESSAGES`). The code stays usable.
- Wrong codes are also counted per email across codes, in the same table: 10 a day (`wrongCodesPerEmail`). Past that every code is refused, the right one too, with `429 too_many_attempts` (`PASSWORD_RESET_MESSAGES.tooManyWrongCodesForEmail`, Retry-After) until the oldest wrong code leaves the window, so asking for a new code gives no more guesses. Rows older than the longest window are deleted whenever a code is requested.
- `POST /members/password-reset/complete` `{ email, code, password }` -> `204`, with no session: the Member signs in with the new password. The same code refusals, and `400 invalid_password` with the sign-up rule (`passwordSchema`). The code is checked and spent in one transaction, committed before Supabase Auth is asked, so a code can never set a password twice: if Supabase Auth then fails the answer is `503 password_reset_unfinished` and the Member asks for a new code. Setting the password through Supabase Auth (`AccountAdmin.setPassword`) ends every session of the account; the test proves it. From then on the reset reports success: `password_reset` is written to the audit log and `passwordChangedEmail("reset", now)` goes out (`members/password-emails.ts`; Change password sends the `"changed"` text), and a failure of either is only logged.
- Both password flows write their audit entries with `recordPasswordEvent` (`members/password-audit.ts`): a failed write is tried once more, and if that fails too the whole entry (type, Member, client address, time; never a password) is logged at error level so it can be added by hand.

## Change password

`members/change-password.ts` (`changeMemberPassword`), route `PUT /members/me/password` in `routes/members.ts`, migration `..._password_change_audit.sql` (audit types `password_changed` and `password_change_failed`). Members only (`requireMember`).

- `PUT /members/me/password` `{ currentPassword, newPassword }` -> `204`. `400 invalid_password` with the sign-up rule (`passwordSchema`) or, when the new password is the current one, `PASSWORD_CHANGE_MESSAGES.samePassword`; `400 invalid_request` for a missing field; `403 current_password_incorrect` ("Current password is incorrect."); `429 too_many_attempts` (Retry-After). The wrong password is a 403 and not a 401 on purpose: the app takes a 401 to mean "your session is gone".
- The current password is checked by signing in with it at Supabase Auth (`AuthProvider.signInWithPassword`); that throwaway session is signed out again. The new password is then set with the Member's own access token (`AuthProvider.changePassword`, `PUT /auth/v1/user`), which makes GoTrue end every OTHER session of the account (access and refresh tokens) and keep this one. `AccountAdmin.setPassword` (used by Forgot password) would end this phone's session too.
- Only a wrong current password counts. `verifyCurrentPassword` alone runs inside the same `AttemptLimiter` as the sign-in routes (`signInLimiter`), so guessing here counts against, and cannot get around, the limit on the sign-in screen; setting the new password (`changeMemberPassword`) runs outside it, so a session that ended meanwhile (401), rejected input and successful changes do not count. A wrong password is written to the audit log as `password_change_failed` (actor and subject: the Member, data `{ clientAddress }`; the password is never recorded). A change is `password_changed` (same shape), then `passwordChangedEmail("changed", now)` goes out. Once the password is changed nothing can fail the request: the audit write (`recordPasswordEvent`, with its one retry) and the email are each tried, and a failure of either is logged and the Member still gets the `204`.
- The request carries the Member and the access token it was signed in with (`memberOf(res)`, `accessTokenOf(res)` in `auth/guards.ts`). A new password that breaks the sign-up rules is refused by `passwordRuleRefusal` (`validation.ts`), shared with Forgot password.
- Hosted Supabase Auth must have "Secure password change" off (`security_update_password_require_reauthentication = false`, the default), or `PUT /user` asks for a reauthentication nonce this API does not send.

Tests: `test/password-change.test.ts` (HTTP against the real Supabase Auth: session rules with three sessions and refresh tokens, audit and email, wrong password, the audit entry for it, the sign-up rules, the same password, who may call, the limit and its sharing with sign-in, a 401 from an ended session not counting, and a failing audit write or email send leaving the change standing; the audit failure is a trigger the test adds to `audit_log` and drops, the email one is `api.emails.failing`, the ended session is `startTestApi({ wrapAuth })`).

## Digital ID and Loan Policy

A Digital ID is 12 digits: the Member's fixed 6-digit Digital ID number, then a 6-digit TOTP-style token (HMAC-SHA-256 of the 60-second window under a 32-byte per-Member secret). ADR 0004 records why. `digital-id/code.ts` is the derivation (pure); `digital-id/index.ts` has `currentDigitalId(deps, memberId)`, which creates the number and secret on first use with the CSPRNG, and `verifyDigitalId(deps, code)`, which accepts the current and the previous window by `deps.clock`, compares in constant time, and throws 400 `digital_id_expired` (up to an hour old) or `digital_id_invalid`. It returns `{ memberId, window }`: the pair that names one shown code, which scanning it at the desk claims for that Librarian (see Loans, desk sessions).

- `GET /members/me/digital-id` (Member) -> `DigitalIdResponse` `{ code, windowStartsAt, refreshAt, serverTime }`, `Cache-Control: no-store`.
- `POST /desk/members/identify` `{ code }` (Librarian) -> `{ member: { id, fullName, accountType, loans: { current, limit, loanPeriodDays } }, deskSession: { token, expiresAt } }`, `Cache-Control: no-store`. It starts a desk session (ADR 0008, `desk/sessions.ts`, see Loans). 400 `invalid_request` unless `code` is exactly 12 digits; 400 `digital_id_expired` / `digital_id_invalid`; 409 `digital_id_used` when another Librarian scanned this code first.
- `public.digital_id_secrets` has no grants for any client role, `service_role` included: only the API, connected as itself, reads it.
- `public.loan_policies` holds one row per Account Type (placeholders created by the migration, and put back by the seed script if missing). Librarians read Member profiles through the `members_read_staff` policy.

Tests: `test/digital-id.test.ts` (HTTP, fake clock), `test/digital-id-code.test.ts` (RFC 6238 vectors).

## Catalog search

`GET /catalog/search?q=<text>&limit=<n>` (`routes/catalog.ts`, behind the one `requireMember` guard) answers `{ query, total, results }`: Books best match first, each with `availableCopies` and `totalCopies`. No match is `200` with an empty `results`; a search that cannot run is a `400 invalid_request` or a 5xx error body. `CatalogSearch` (`catalog/catalog-search.ts`) holds one immutable index built with the shared search module (`@libras/shared`: `buildCatalogIndex`, the flat trie of ADR 0001). Every change to Books or to what identifies a Copy bumps `catalog_revision` (statement triggers); a search that sees a newer revision starts one rebuild in the background and keeps answering from the current index until the new one is swapped in with a single assignment, so a search in flight is never disturbed. A catalog change therefore shows in results a moment later, not on the very next request: a test that changes the catalog waits with `eventually` (`test/eventually.ts`). Availability is read from the Copies for the matched Books on every search. `npm run measure:search -w @libras/api` measures latency over HTTP on the seeded catalog (`npm run seed` first).

## Holds

`src/holds/`, `routes/holds.ts` and the migration `supabase/migrations/20261112200000_holds.sql`. A Hold is a Member's place in the queue for a Book that has no available Copy.

- `POST /holds` `{ bookId }` (Member) -> `201 { hold }`, status `waiting`. Refused with `403 cannot_borrow` (Visitor and Alumni, by `canBorrow`), `404 book_not_found`, `409 copy_available` (a Copy is `available` now: borrow it instead; this is the same live count the Book page shows), `409 overdue_loan` or `409 unsettled_fine` (not in Good standing, words in `GOOD_STANDING_MESSAGES`, the sentence the Book page shows), `409 book_on_loan` (the Member has a Copy of the Book on Loan: their own return would otherwise set it aside for them again) and `409 hold_exists` (the Member already has a `waiting` or `ready` Hold on the Book; only that unique index is reported this way, by its name). A Book with no Copies at all can be held.
- `GET /members/me/holds` (Member) -> `{ holds }`: every Hold of the Member, active ones (`waiting`, `ready`) first, each group newest first. Each has `pickupEndsAt`: the end of the Pickup Window once the Hold has been chosen, null before. The Member's own ended windows are expired first, so a `ready` Hold in the list always has a window that is still running. Read through `withIdentity`, so row-level security is the second layer.
- `POST /holds/:id/cancel` (Member) -> `{ hold }`, status `cancelled`. A `waiting` Hold leaves the queue. A `ready` Hold gives up its set-aside Copy, which in the same transaction goes to the Book's next waiting Hold (with a Pickup Window of its own from the cancel, an email and an audit entry) or becomes available when nobody waits. A `fulfilled`, `expired` or `cancelled` Hold is `409 hold_not_cancellable`, and so is a `ready` Hold whose Pickup Window has ended (it is expired on the spot: see Pickup Window expiry); `409 hold_conflict` only if the Hold changed three times while the request waited. A Hold that is not the Member's is `404 hold_not_found`, the same as one that does not exist.
- The table keeps what the dispatcher of ADR 0001 needs: `placed_at` (arrival, from `deps.clock`), `weight_hours` (Faculty 24, NTP / Employee 12, UMAK Student 0: `HOLD_WEIGHT_HOURS`), `score` (`placed_at` minus the weight, a check constraint keeps them in step) and `seq` (arrival order). The queue of a Book is its `waiting` Holds ordered by `(score, seq)`, served by the partial index `holds_queue_idx`. There is no in-memory queue. The states are `waiting`, `ready`, `fulfilled`, `expired`, `cancelled`. A Hold that was chosen keeps `copy_id`, `ready_at` and `pickup_ends_at`, and `fulfilled_at` once its Member borrowed the Copy and `expired_at` once its window was ended.
- At most one active Hold per Member per Book is enforced by the partial unique index `holds_one_active_per_member_and_book`, so two requests at once cannot both succeed (the second is `409 hold_exists`). After a cancel the Member may place a new Hold.
- Clients have `select` only, on their own rows (`holds_read_own`). The API writes Holds as itself.
- Placing a Hold reads the Book's Copies with a shared row lock, so it waits for a return of one of them that is in progress and then sees its outcome (see Hold dispatch).

Tests: `test/holds.test.ts` (HTTP: placing, every refusal, cancelling, privacy, the row-level security check through a route that queries as the signed-in Member, the dispatcher's columns) and the pure weights.

## Hold dispatch

`src/holds/dispatch.ts` and the migration `supabase/migrations/20261113140000_hold_dispatch.sql`. ADR 0001 has the algorithm, ADR 0006 the locks and the decisions.

- **`dispatchCopy(deps, tx, copy, { at, cause, actorId, causeEntries? })`** places a Copy that nobody has any more. One query (`DISPATCH_SQL`) makes the Book's waiting Hold with the lowest `(score, seq)` `ready` for this Copy: `copy_id`, `ready_at = at` and `pickup_ends_at = at` plus `library_settings.pickup_window_hours` (one row, seeded as 24). The Copy becomes `set_aside`, or `available` when no Hold was waiting. It records the audit entries of what freed the Copy when the caller passes them (`causeEntries`: `copy_returned` and a late return's `fine_fixed`, or `hold_expired`), then the audit event `hold_dispatched` (subject: the Hold; data `{ memberId, copyId, bookId, accessionNumber, pickupEndsAt, cause }`; actor: whoever freed the Copy) and returns a `HoldDispatch` (the Member's name and email, the Book, the end of the Pickup Window) or null. Call it last in the transaction and write nothing to the audit log before it: the audit log serialises its writers, so every entry is written after all other work, and it reads cause, then effect.
- **The caller's rules.** Call it inside the transaction that freed the Copy, with the Copy's row locked (`lockCopy` in `src/copies`, by scan or by id), and call it last, because it writes the audit log. After the commit, pass the result to `announceDispatch(deps, dispatch)`, which sends the Hold-ready email (`holdReadyEmail`) and only logs a failure to send. The lock order of every writer is the Member's row, the Copy's row, then a Hold's row.
- **Who calls it.** `recordReturn` (cause `copy_returned`, actor the Librarian) and `cancelHold` for a ready Hold (cause `hold_cancelled`, actor the Member). Pickup Window expiry is the third (cause `pickup_window_expired`, no actor).
- **The desk.** `POST /desk/returns` answers `loan.heldFor`: `{ memberName, pickupEndsAt }` when the returned Copy is now set aside, null when it is available.
- **Borrowing the set-aside Copy.** `takeCopy` in `src/loans/index.ts` is the one place that decides whether a Copy may go out to a Member. A `set_aside` Copy goes only to the Member whose `ready` Hold has that `copy_id`, and only while `pickup_ends_at > now`; the Hold becomes `fulfilled` in the Loan's transaction; anyone else gets `409 copy_set_aside`. When the window has ended but nobody has expired the Hold yet, the confirmation expires it and runs again (see Pickup Window expiry).
- **The database's own word.** `holds_one_ready_per_copy` (at most one ready Hold per Copy), and check constraints: a waiting Hold has no Copy, a ready one has a Copy and a Pickup Window, `fulfilled_at` goes with `fulfilled`.

Tests: `test/hold-dispatch.test.ts` (HTTP: a return makes the Hold ready and sets the Copy aside; no Hold, the Copy is available; the email; the order by role weights with Faculty and NTP / Employee Members made by the fixture `memberWithHold`, because their sign-up is not built yet; the stored Pickup Window length; the refusal to other Members; fulfilment; the audit entry; cancelling a ready Hold; and "Hold dispatch at the same moment": several Copies of one Book returned at once at two desks, a return against a cancel, against Loans and against Holds being placed, and four races with a fixed order, made by holding the audit log so that the first request has done everything but commit). Removing `for update skip locked` from the dispatch query, the `for update` of `cancelHold` or the `for share` of `placeHold` each makes a test there fail. Removing only the Copy's row lock fails none of them, because the Hold's row lock and the guards on the Loan and the Hold still decide those races; the Copy lock is kept for the lock order (without it a cancel and a Loan can deadlock) and because `dispatchCopy` relies on it.

## Pickup Window expiry

`src/holds/expiry.ts`, `src/sweep.ts`, `routes/sweeps.ts`, `scripts/pickup-sweep-schedule.ts` and the migration `supabase/migrations/20261113160000_pickup_expiry.sql` (`holds.expired_at`, an index on the ready Holds' `pickup_ends_at`, the audit event type `hold_expired`). ADR 0007 has the decisions.

- **`expireHold(deps, holdId)`** ends one window if it has passed (`pickup_ends_at <= now`): reads the Hold without a lock, locks the Copy (`lockCopy`), locks the Hold, checks it is still `ready` and due, sets it `expired` with `expired_at`, then `dispatchCopy` with cause `pickup_window_expired`, which records `hold_expired` (its `causeEntry`; subject: the Hold; data `{ memberId, copyId, bookId, accessionNumber, pickupEndsAt, expiredAt }`; no actor) before its own entry (the next waiting Hold gets a Pickup Window of its own from now, an email and a `hold_dispatched` entry, or the Copy becomes available), and sends the email after the commit. It answers `expired` or `skipped` (the Hold was borrowed, cancelled or not due).
- **`expireDueHolds(deps, { memberId? })`** is the sweep: every due ready Hold (or one Member's), oldest window first, one transaction each; a failure is logged and the others go on. It returns how many it expired.
- **Who runs it.** The sweep tick (`runSweep` in `src/sweep.ts`, which runs Loan notices after it): `startSweeper(deps)` every 60 seconds from `server.ts` (and the end-to-end server); `POST /internal/sweeps/pickup-expiry` with `Authorization: Bearer <SWEEP_SECRET>` (`200 { expired, noticeEmails }`, `401 invalid_sweep_secret`; the path keeps its old name because the hosted schedule calls it; no route at all when `SWEEP_SECRET` is unset), which the database's pg_cron schedule calls every five minutes to wake a sleeping service (`npm run schedule:hosted`, root README); and the three places that must not see an ended window as open: `takeCopy` (a Loan after the window expires the Hold and runs again, as if the sweep had run first), `cancelHold` (refused as `hold_not_cancellable`) and `listHolds`.
- **Tests** (`test/pickup-expiry.test.ts`, all on the fake clock): `api.sweepPickupWindows()` runs the expiry alone, `api.sweep()` the whole tick; `startTestApi({ sweepIntervalMs })` runs the real timer; `startTestApi({ sweepSecret })` mounts the endpoint. Reading a Hold through the API expires it if due, so to look at a Hold the sweep has not touched, read `public.holds` directly. `test/pickup-sweep-schedule.test.ts` runs the database schedule's SQL against the local Supabase (pg_cron, pg_net, vault).

## Loan notices

`src/notices/` and the migration `supabase/migrations/20261117160000_loan_notices.sql`. ADR 0009 has the decisions.

- **When.** `noticeDue(dueAt, now)` in `schedule.ts` is the one place that decides it. The due-tomorrow notice is due from 08:00 library time on the day before the due date until the Loan is overdue. The now-overdue notice is due from 08:00 on the first overdue day, for 7 days. Still-overdue repeats 1 to 4 follow every 7 days, each due for 7 days. Only the latest notice whose time has come is due, so the job skips an out-of-date notice. It sends no due-tomorrow notice once the Loan is overdue, sends a missed repeat once, and sends nothing after the fourth repeat's week. A returned Loan gets none.
- **The job.** `sendLoanNotices(deps)` runs on every sweep tick and returns how many emails went out. It finds current Loans with a notice due and no record of it for the current `due_at`, so a Renewal gives the Loan a fresh set. Each Member gets one email covering all of them (`loanNoticeEmail`). Overdue Loans come first, then the ones due tomorrow, and each due-tomorrow Loan says whether it can be renewed (`renewalOf`) and the Member's daily Fine rate and cap. Each overdue Loan states its Fine so far (`fineAt`, the same amount My Loans shows at that moment).
- **At most one email a Member a library day.** Each Member gets one transaction. It inserts the Member's row in `loan_notice_emails` (unique per Member and library day), reads the Member's due notices again, inserts a `loan_notices` row for each (primary key Loan, kind, due date and repeat), sends, and commits only after the sender accepted. A refused send rolls everything back and the next tick tries again. A send whose outcome is unknown (`EmailOutcomeUnknownError`: Brevo did not answer within its 15 second timeout and may have accepted the email) keeps only the email row, with `outcome = 'unknown'`, so no later tick that library day mails the Member again, and the notices still due go out on the next library day (ADR 0009). The job logs a failure and goes on with the other Members. A second tick at the same moment waits on the email row and then sends nothing. A notice that comes due after the Member's email of the day, such as a Loan lent later that day and due the next, waits until 08:00 the next day and says "due today". The transaction holds a connection while the email is sent (Brevo's timeout is 15 seconds) and locks no Loan, Member or Copy. If the API stops after Brevo accepted an email and before the commit, the next tick sends it again, which ADR 0009 accepts.
- **Not here.** The audit log does not record notices, and Members cannot switch them off. No client role can read either table.
- **Tests** (`test/loan-notices.test.ts`, on the fake clock with captured emails) cover every kind on its days, never before 08:00, one email per Member per day, failed send and retry, out-of-date and missed notices, returned and renewed Loans, the renewal and Fine sentences, two overlapping ticks (the capturing sender's `hold()` keeps the first email in flight), the endpoint, the timer, and each job still running when the other fails (made to fail by renaming a column or table for the length of one tick).

## Loans

`src/loans/`, `routes/loans.ts` and the migration `supabase/migrations/20261112220000_loans.sql`. A Loan exists only once a Librarian confirms it at the desk; no Member endpoint creates one, and clients have `select` only on `public.loans`.

- **Desk sessions** (ADR 0008, `src/desk/sessions.ts`, table `public.desk_sessions`). Scanning a Digital ID (`POST /desk/members/identify`) checks it once and starts a session for that Librarian and Member: a 32-byte random token (base64url; only its SHA-256 hash is stored) that ends 10 minutes after its last use (`DESK_SESSION_MINUTES`). `useDeskSession` renews it on every Copy scanned with it, confirmed or refused. `POST /desk/sessions/end` `{ deskSession }` (Librarian) -> `204` ends it at once ("Done with this Member"); it does nothing for a token that is not a live session of that Librarian's. A token that is unknown, expired, ended or another Librarian's gets `409 desk_session_ended` (`LOAN_MESSAGES.deskSessionEnded`: scan the Digital ID again). No client role can read the table.
- `POST /desk/loans` `{ deskSession, copy }` (Librarian) -> `201 { loan, member }`. `deskSession` is the token the scan of the Member's Digital ID gave, `copy` is the Copy's barcode or its accession number (typed in either case). `loan` is `{ id, bookTitle, accessionNumber, checkedOutAt, dueAt }` and `member` is the `DeskMember` with the Loan counted. Refusals, each with a message the desk page shows (`LOAN_MESSAGES`): `400 invalid_request`, `409 desk_session_ended`, `404 copy_not_found`, `403 cannot_borrow` (Loan Policy limit of zero: Visitor, Alumni), `409 overdue_loan` or `409 unsettled_fine` (not in Good standing, also for the Copy set aside for the Member's own ready Hold, which stays ready; `LOAN_MESSAGES.notInGoodStanding`), `409 loan_limit_reached`, `409 copy_on_loan`, `409 copy_set_aside` (set aside for another Member's Hold).
- `GET /members/me/loans` (Member) -> `{ loans, loanLimit, loanPeriodDays }`: every Loan of the Member, current ones first (due soonest at the top), then returned ones. Each has `checkedOutAt`, `dueAt`, `returnedAt`, `overdue` (still out and past `dueAt` by `deps.clock`), `renewalCount`, `renewal` (see Renewals; null for a returned Loan) and `fine` (see Fines; null when there is none). Read through `withIdentity`, so row-level security is the second layer (`loans_read_own`; Librarians read all through `loans_read_staff`, which is how the desk counts a Member's Loans).
- **Due date.** `loanDueAt` (`@libras/shared`): the last millisecond of the library day (UTC+8, `LIBRARY_UTC_OFFSET_HOURS`) that is the Loan Policy's `loan_period_days` after the checkout day. A Loan is overdue from the next day.
- **One transaction** (`confirmLoan`): lock the Member's row, then the Copy's row (`for no key update`), check the limit and the Copy's status, insert the Loan, set the Copy `on_loan`, record the audit event `loan_confirmed` last. Setting the Copy `on_loan` is what makes the live count of available Copies fall for search, the Book page and the Hold action. Two requests at once for one Copy, or for a Member's last allowed Loan, yield exactly one Loan; the partial unique index `loans_one_open_per_copy` (one open Loan per Copy) is the database's own backstop. Any later writer that needs both locks (returns, Hold dispatch) must take them in the same order: Member, then Copy.
- **An open Loan** is one with `returned_at` null. A return sets `returned_at` and frees the Copy; My Loans then lists it as past.
- **Returns.** `POST /desk/returns` `{ copy }` (Librarian; the Copy's barcode or accession number, with no Member involved) -> `200 { loan }`, where `loan` is `{ id, bookTitle, accessionNumber, memberName, checkedOutAt, dueAt, returnedAt, late, fine, heldFor }` (`late`: back after its due day; `fine`: the Fine this return fixed, or null; see Fines). Refusals, with the words in `RETURN_MESSAGES`: `400 invalid_request`, `404 copy_not_found`, `409 copy_not_on_loan` (on the shelf, set aside, or already returned), `409 return_conflict` (the Copy changed hands three times while the request waited; scan again). `recordReturn` in `src/loans/index.ts` is one transaction: an unlocked read finds who has the Copy out, then it locks that Member's row and the Copy's row (the same order as `confirmLoan`), reads the open Loan again, sets `returned_at`, fixes a late Copy's Fine (`fixFine`) and calls `dispatchCopy` last (see Hold dispatch), which records the audit event `copy_returned`, then `fine_fixed` for a Fine, then, when a Hold was chosen, `hold_dispatched`. `loan.heldFor` says whose Hold the Copy is now set aside for, or is null. Two returns of one Copy at the same moment yield one return, one audit entry and one `copy_not_on_loan`.
- **Set-aside Copies.** `takeCopy` in `src/loans/index.ts` is the one place that decides whether a Copy may go out to a Member: a `set_aside` Copy goes only to the Member of its ready Hold, which becomes `fulfilled` (see Hold dispatch).
- **Renewals** (migration `20261117100000_renewals.sql`). `public.loan_policies.renewal_limit` (seeded as 1) and `public.loans.renewal_count`. `POST /loans/:id/renew` (Member, no body) -> `200 { loan }`: the Loan as My Loans lists it, with `dueAt` one loan period after the old due date (`renewedDueAt`: the old due date plus whole days, so it stays the last millisecond of a library day) and `renewalCount` one higher. Refusals: `400 invalid_request` (not a uuid), `404 loan_not_found` (no such Loan, or another Member's), `409 loan_returned`, and the `RENEWAL_REFUSALS`, each `409` with its code, checked in this order: `loan_overdue`, `renewal_limit_reached`, `hold_waiting` (another Member's `waiting` Hold on the Book; a `ready` one does not block), then `overdue_loan` (another of the Member's Loans is overdue) or `unsettled_fine` (not in Good standing). Words in `RENEWAL_MESSAGES`. `renewalOf(facts, now)` in `renewability.ts` is the one place that decides, for the Loans list (`renewal`: `{ renewable: true, dueAt, last }` or `{ renewable: false, reason }`) and for the Renewal itself; `booksWithWaitingHolds` reads other Members' Holds as the API (row-level security hides them from the Member). `renewLoan` is one transaction: lock the Member's row (`lockMember`, `policy.ts`), then the Copy's, read the Loan and the Book's waiting Holds, update the Loan, record the audit event `loan_renewed` (actor: the Member) last. No email is sent. A return reads the current `due_at`, so the desk sees the renewed date.
- **Used Digital IDs.** `public.digital_id_uses` records the Member and window of a code scanned at the desk, and the Librarian who scanned it first (when the desk session starts). That Librarian may scan the same code again while it is still accepted; any other Librarian gets `digital_id_used` and no session. No client role can read the table.

Tests: `test/loans.test.ts` (HTTP: confirmation and due date, availability falling, every refusal, the audit entry, the desk session on the fake clock (a Copy minutes after the Digital ID, renewal, expiry, Done, another Librarian, every Loan rule still checked), three races, My Loans order and overdue with the fake clock, privacy and the row-level security checks).

`test/renewals.test.ts` (HTTP: the Loans list and the new due date, each refusal, a renewal limit above one, a ready Hold not blocking, only the Member's own Loan, a returned Loan, the audit entry, no email, the return after a Renewal; and three races with a fixed order: a Renewal against a Hold being placed, either one first, and against a return). Removing the Copy's row lock from `renewLoan` fails both Hold races.

`test/returns.test.ts` (HTTP: a return closes the Loan, frees the Copy and moves the Loan to the Member's past Loans with its return date; typed accession numbers; availability in search and on the Book page; the loan limit freed; a late return; every refusal; Librarian only; the audit entry; and the races: two Librarians returning one Copy, a burst of ten scans of one Copy, and returns mixed with Loans for the same Members). `test/loans-harness.ts` holds what the Loan and return tests share.

## Fines

`src/fines/` and the migration `supabase/migrations/20261117180000_fines.sql`. ADR 0010 has the decisions. Every amount is whole centavos (`500` = PHP 5), in the database and in the JSON; `formatPesos` (`@libras/shared`) writes it as "PHP 5" or "PHP 2.50".

- **Policy.** `public.loan_policies.fine_daily_rate_centavos` and `fine_cap_centavos`, seeded as 500 and 30000 (PHP 5 a day, at most PHP 300) for UMAK Student, Faculty and NTP / Employee, and 0 for Visitor and Alumni, who cannot borrow. Placeholders until the library confirms the real numbers: a data change.
- **The amount.** `fineAt(dueAt, policy, at)` is the one place that computes it: the daily rate times the calendar library days (UTC+8) after the due date, the day of `at` included, up to the cap. No grace period: the first moment after the due date is one day late. Null when the Loan is not overdue or the amount would be zero. My Loans (the Fine so far, under the current policy), the return and the Loan notices all call it.
- **Fixed at the return.** `fixFine` runs inside `recordReturn` with the Member's row locked and inserts one `public.fines` row: `loan_id` (primary key), `member_id`, `days_late`, `daily_rate_centavos`, `cap_centavos`, `amount_centavos`, `fixed_at`. The row never changes; a later policy change does not touch it (a check constraint keeps the amount equal to `least(days_late * rate, cap)`). A Copy back on time, or under a rate of zero, gets no row. The audit event `fine_fixed` (actor: the Librarian; subject: the Loan; data `{ memberId, daysLate, dailyRateCentavos, capCentavos, amountCentavos }`) follows `copy_returned`. Loans returned before the migration have no Fine.
- **Reading.** `LoanFine` (`@libras/shared`) is `{ amountCentavos, daysLate, dailyRateCentavos, capCentavos, final, settlement }` (`settlement` is `{ outcome: "paid" | "waived", settledAt }`, or null while the Fine is unsettled or the Loan is still out). `GET /members/me/loans` gives each Loan's `fine`: computed (`final: false`) while it is out and overdue, the stored row (`final: true`) once returned. `POST /desk/returns` gives the fixed one. `LOAN_SELECT` (`my-loans.ts`) left-joins `public.fines` as `f` (`FINE_COLUMNS`, `storedFine`).
- **Row-level security.** Clients have `select` only. `fines_read_own` (a Member reads their own) and `fines_read_staff` (a Librarian reads any). The Loans list reads through `withIdentity`, so the policy applies there too.

- **Settling** (migration `20261117200000_fine_settlement.sql`, `src/fines/settle.ts`, route `src/routes/fines.ts`). `POST /desk/fines/settle` (Librarian only) takes `{ place: "return", loan, outcome }` or `{ place: "desk_session", deskSession, loan, outcome }`, `outcome` being `paid` or `waived`, and answers `{ loanId, settlement, member }` (`member` is the Fine's Member as the desk now shows them). The Fine's own row holds the settlement: `settled_outcome` (`fine_outcome` enum), `settled_by`, `settled_at`, all null or all set (`fines_settlement_complete`); LIBRAS keeps no money amount. `fixed_by` is the Librarian whose return fixed the Fine (null only for a Fine the migration could not attribute from the audit log; a NOT VALID check `fines_fixed_by_present` makes every new Fine name one). The 10-minute rule on the return screen is deliberate: on a `return` only that Librarian may settle, up to `SETTLE_AT_RETURN_MINUTES` (10) after the return (`409 settle_at_return_ended`, then the desk session is the place); in a `desk_session` the Fine must belong to that session's Member (the session is renewed like for any Copy, and `409 desk_session_ended` when it is over). A Fine with a null `fixed_by` cannot be settled on a return (404), only in a desk session. **Who stays private:** `authenticated` has column privileges on `public.fines` that leave out `fixed_by` and `settled_by`, so a Member reading their Fine through Supabase sees the amount, how and when it was settled, not which Librarian; only the API (as postgres) reads those two. `select *` is refused for the client roles. A Fine that is not there for the caller (unknown, another Member's, another Librarian's return) is `404 fine_not_found`; a settled one is `409 fine_already_settled` and is never changed (no way back). Locks: the Member's row (`lockMember`), then the Fine's row `for update`; the update is guarded by `settled_at is null`, so two settlements at once give one winner. The audit event `fine_settled` (actor: the Librarian, subject: the Loan, data `{ memberId, outcome, amountCentavos, place }`) is recorded last in the transaction. The desk Member panel lists the Fines from `DeskMember.clearance.unsettledFines` (`UnsettledFine[]`, earliest return first), read as the Librarian by `deskMember` in `src/desk/members.ts`; it is in `POST /desk/members/identify`, `POST /desk/loans` and the settle response. A Member's unsettled Fines are the `public.fines` rows with `settled_at is null` (index `fines_unsettled_idx`).

- **Clearance and Good standing** (`src/standing/index.ts`, ADR 0010; nothing is stored). `readStanding(scope, memberId, now)` reads the Member's Loans still out (`public.loans` with `returned_at is null`, the one due soonest first, each with `overdue` by the API's clock) and their unsettled Fines (the `fines` rows with `settled_at is null`, the earliest return first). Two pure functions work the answers out of that: `clearanceOf` (cleared = no Loan out, on time or not, and no unsettled Fine; `{ cleared, loansOut, unsettledFines }`) and `goodStandingOf` (no overdue Loan and no unsettled Fine; `{ inGoodStanding: true }` or `{ inGoodStanding: false, reasons }` with reason codes `overdue_loan` and `unsettled_fine`, named in that order). A Loan out and overdue has no Fine yet, so it shows in `loansOut` only. `GET /members/me/clearance` (Member) -> `{ clearance, goodStanding }`, read as the Member so row-level security shows only their own. The desk's `DeskMember` carries the same `clearance` (its only copy of the unsettled Fines; `deskMember` takes `{ db, librarian, memberId, now }`) (identify, confirm-Loan and settle responses). **Refusals without Good standing.** Confirming a Loan, placing a Hold and making a Renewal are refused, `409` with the reason as the code: `overdue_loan` or, failing that, `unsettled_fine` (`goodStandingRefusal` names the first of `GOOD_STANDING_REFUSALS`; the Profile gets them all). Each reads Good standing inside its own transaction after `lockMember`: `confirmLoan` and `placeHold` through `requireGoodStanding` (with their own words), `renewLoan` through `renewalOf`'s `notInGoodStanding` fact. A return fixes a Fine and a settle changes one under that same lock, so the answer is never older than the action; a settle that is committing when a Loan, Hold or Renewal arrives makes it wait and then go through (`placeHold` takes `lockMember` for this since #39). The Loans list (`listLoans`, read as the Member) and the due-tomorrow Loan notice supply the same fact to `renewalOf`, so My Loans and the email say why before the Member tries. Ready Hold, unsettled Fine: the Loan is refused and the Hold stays ready; once a Librarian settles the Fine in the same desk session, the next scan of the Copy lends it.

Tests: `test/fine-settlement.test.ts` (both places and both outcomes with the audit entry, the Member panel list, settling twice in either place, two Librarians at the same moment, refusals for a Member, no session, another Librarian, an expired window, another Member's Fine, an ended desk session, malformed bodies, refused database writes and the all-or-nothing check) and `test/fines.test.ts` (HTTP on the fake clock: no Fine until the due date ends, then by day; the cap; fixed at the return, the day of the return counted, with the Member's name for the desk; unchanged after a rate and cap change while a Loan still out follows the new policy; nothing for an on-time return; the audit entry; row-level security, read from `public.fines` alone so that the Loans policy cannot hide a leak, and refused writes). The notice sentences are in `test/loan-notices.test.ts`. Clearance: `test/clearance.test.ts` (cleared; blocked by a Loan out and on time, by an overdue Loan with no Fine yet, by a Fine; cleared again after the return and after settling, paid or waived; ordering; a Member sees only their own; every Account Type; signed-in Members only) and `test/good-standing.test.ts` (the Good standing rule apart from Clearance). Refusals: `test/good-standing-refusals.test.ts` (each of the three actions for each reason; the ready Hold kept and lent after a settle in the same session; both reasons at once; the Profile's `goodStanding`; and three races in the style of `pickup-expiry.test.ts`, a settle held at the audit log while a Loan, a Hold and a Renewal wait for it and then go through; removing `lockMember` from `placeHold` fails the Hold one).

## Announcements

`src/announcements/`, the route `src/routes/announcements.ts` and the migration `supabase/migrations/20261119120000_announcements.sql` (spec #42). An Announcement is a poster image every Member sees on Home, with a title, optional text, one optional link (a Book or an https web page) and a first and last day.

- **Time.** It shows from the start of its first library day (00:00 Manila) to the end of its last: `starts_at` and `ends_at` (exclusive). End now moves `ends_at` to the API's `now`. The status is worked out on each read by the API's clock: `running`, `scheduled` or `past`.
- **One at a time.** The exclusion constraint `announcements_one_at_a_time` (`exclude using gist (tstzrange(starts_at, ends_at, '[)') with &&)`) refuses an overlap in the database, so two overlapping saves at the same moment give one winner. The API also looks for an overlap first, so it can name the one in the way before storing any image. Either way the refusal is `409 announcement_overlap` with that Announcement's title and days (`announcementOverlapMessage`).
- **Images.** The upload never reaches Storage. `preparePoster` checks the size (5 MB; a larger request body is refused unread by `express.raw`, also as `413 announcement_image_too_large`), the real type from the first bytes and then from sharp (`announcement_image_type`: JPG, PNG or WebP only), refuses decompression bombs (50 megapixels) and posters too small for a sharp banner (`announcement_image_too_small`: a 2:1 crop under 600 px wide), turns the picture upright and writes two new JPEGs with no metadata at all: the poster fitted into 1200 x 2400, and the 2:1 banner cut from it at `crop_position` (0 to 1 along the poster's long side, as the desk page's frame moves), at most 1200 x 600. Both go to the public bucket `announcements` as `<id>/<random uuid>.jpg`; a new image or crop gets new names, then the old files are removed, so a cached file never shows for a newer one. A crop change alone reads the stored poster back and cuts a new banner. Files are written before the row and removed again when the row is refused; a file that cannot be removed is logged and only wastes space.
- **The bucket.** Created by the migration (public read, 5 MB, `image/jpeg` only). No policy on `storage.objects` lets `anon` or `authenticated` write, so only the secret key (the API) can. Locally `supabase/config.toml` runs Storage (`[storage] enabled = true`).
- **Endpoints** (Librarian only; `401 not_signed_in`, `403 not_staff` otherwise). `GET /desk/announcements` -> `{ running, scheduled, past }` (`DeskAnnouncementsResponse`; scheduled soonest first, the 50 latest past). `POST /desk/announcements` (multipart: `details` JSON per `announcementDetailsSchema`, `image` file) -> `201 { announcement }`. `PUT /desk/announcements/:id` (the same form; `image` only to replace the poster) -> `{ announcement }`, refused for a past one (`409 announcement_past`) and when another desk saved it in between (`409 announcement_changed`); a running one keeps its first day, which is behind it. `POST /desk/announcements/:id/end` (the running one only: `409 announcement_not_running` for a scheduled one). `DELETE /desk/announcements/:id` -> `204` (a scheduled one only: `409 announcement_not_scheduled`). `GET /desk/announcements/books?q=` -> `{ books }`, the catalog search for the link picker. Bad details are `400 invalid_request` with the first problem in words (`ANNOUNCEMENT_MESSAGES`), an unknown Book `400 book_not_found`, a Storage failure `502 announcement_storage_failed`.
- **Audit.** `announcement_created` and `announcement_edited` (data `{ title, firstDay, lastDay, link, linkTarget }`, plus `imageReplaced` for an edit; `linkTarget` is the Book id or the web address), `announcement_ended` (`{ title, endsAt, plannedLastDay }`) and `announcement_deleted` (`{ title, firstDay, lastDay }`), actor the Librarian, subject the Announcement, recorded last in the transaction.
- **Members** never read the table (no grants, row-level security on). Home gets the running one through `runningAnnouncement(deps, now)`.

Tests: `test/announcements.test.ts` (HTTP on the fake clock, real local Storage: create with both images and no location metadata, the crop of a tall and a wide poster, refusals for Members and signed-out callers, an overlap named, two overlapping creates at once five times over, each refused file, link and date, a Book link and the Book search, the running and past states by the clock, edits that replace the image or only the crop, an overlapping edit, End now, Delete, and the audit entries).

## The phone scanner

ADR 0005 has the transport decision. `src/scanner/hub.ts` (`ScannerHub`, in memory, one per app) and `src/routes/scanner.ts` are the whole feature; nothing touches the database.

| Endpoint | Who | What |
| --- | --- | --- |
| `GET /desk/scanner/events[?desk=<id>]` | Librarian | A `text/event-stream`. Events (`DeskScannerEvents` in `@libras/shared`): `desk` (the desk id), `pairing` (a six-digit code valid 120 s, re-sent when it changes), `paired`, `unpaired`, `scan` (`{text}`), `end` (the stream's 30 minutes are up: reconnect with `?desk=`). A comment line every 15 s. `?desk=` takes the earlier pairing back for the same Librarian within 60 s of the stream dropping |
| `POST /desk/scanner/unpair {deskId}` | Librarian | Ends the pairing of one of their desk pages (204, also for an id that is not theirs) |
| `POST /scanner/pair {code}` | nobody | The phone's code (spaces allowed) -> `{token}`. 403 `pairing_code_invalid` for a wrong, used or expired code (one message for all three); 429 `too_many_attempts` after 5 wrong codes in 5 minutes per client address |
| `POST /scanner/scans {text}` | scanner token | 202. 400 `scan_rejected` unless `readScan` accepts it (the same whitelist the desk page applies), 401 `pairing_lost`, 409 `desk_offline` (the desk page's stream is away), 429 `too_many_scans` (30 in 10 s) |
| `GET /scanner/status` | scanner token | `{deskOnline}`, or 401 `pairing_lost` |
| `DELETE /scanner/pairing` | scanner token | The phone leaves (204); the desk page gets `unpaired` and a new code |

The scanner token (32 random bytes, kept only as a SHA-256 hash in memory) is not a Supabase session: every Librarian and Member endpoint refuses it (tested against each desk endpoint). A pairing code names one desk page, belongs to the Librarian whose stream showed it, and is cleared when used. Time (code life, grace, scan window) comes from `deps.clock`, so tests move it; `AppOptions.scanner` and `AppOptions.pairingLimit` change the numbers in tests. `test/scanner.test.ts` reads the stream the way the browser does (`readEventStream` from `@libras/shared`).

## Audit log

`src/audit/` and the migration `supabase/migrations/20261112131200_audit_log.sql`. An append-only log of failed sign-ins, password resets, confirmed Loans, Renewals, returns, Fines fixed at a return and settled, Hold dispatches and Hold expiries. Each entry stores a SHA-256 hash over its content and the previous entry's hash.

- **Record:** `createAuditLog(deps).record({ type, actorId?, subject?, data }, tx?)`. Time comes from `deps.clock`. Pass the client of a transaction (`withTransaction(deps.db, (tx) => ...)`) to record atomically with a change; record last in that transaction, because other writers of the log wait for it to end. The transaction must be READ COMMITTED (the default); the database refuses others.
- **Whitelist:** event types and the exact shape of `subject` and `data` are in `src/audit/events.ts` (strict objects, so an unlisted field such as a password cannot be recorded). The database has its own list, `public.audit_event_types`: a new type needs an entry in `events.ts` and an `insert` in a migration.
- **Chain:** the database, not the API, assigns the gapless `seq`, the `prev_hash` and the `hash` in a BEFORE INSERT trigger that holds an advisory lock until the transaction ends. Updates, deletes and TRUNCATE are refused by ENABLE ALWAYS triggers; `anon`, `authenticated` and `service_role` have no privileges, and row-level security is on with no policy.
- **Verify:** `createAuditLog(deps).verify({ anchor? })` recomputes every hash in TypeScript (`src/audit/canonical.ts`) and reports `content_changed`, `broken_link`, `missing_entry` or `anchor_mismatch` with the entry. From a terminal: `npm run audit:verify -w @libras/api` (local) or `npm run audit:verify:hosted -w @libras/api` (reads `.env.hosted`), optionally `-- --anchor <seq>:<hash>`.
- **Limits:** the table owner (the role migrations and the API use) can still ALTER or DROP the table or disable the triggers. Changes made that way are detected by verification, except removing the newest entries, or rewriting every entry from the changed one onwards; only a head (`seq:hash`) kept outside the database and passed as `anchor` detects those.
