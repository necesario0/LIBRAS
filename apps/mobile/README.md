# @libras/mobile

The Member mobile app: React Native with TypeScript, built with Expo SDK 58 (React Native 0.88, new architecture) and Expo Router, targeting an Android APK (ADR 0002). It talks only to the API (`apps/api`) and takes shared types from `@libras/shared`.

Today it has the welcome screen and the sign-up flow for all five Account Types (account type, name, the details that Account Type gives, username and password, email, emailed code, welcome). The details step is `student.tsx`, `faculty.tsx`, `ntp-employee.tsx`, `visitor.tsx` or `alumni.tsx` in `app/sign-up/`; `src/sign-up/request.ts` maps the Account Type to its step and builds its request. Faculty, NTP / Employee and UMAK Student share `src/sign-up/CollegeIdStep.tsx`. Faculty and NTP / Employee need an `@umak.edu.ph` email; Visitor and Alumni accept any. `libras://status` opens the developer screen that calls `GET /health`.

## Layout

| Path | What |
| --- | --- |
| `app/` | Expo Router screens: one file is one route. `_layout.tsx` loads Montserrat and holds the navigation stack |
| `src/theme/tokens.ts` | Color, type, spacing and radius tokens, defined once from the Figma frames |
| `src/api/client.ts` | The API client: every endpoint is a method, every failure is an `ApiError` |
| `src/auth/` | The Member's session: `AuthProvider` and `useAuth()` (`AuthContext.tsx`), the logic that renews it (`SessionManager.ts`) and where it is kept (`session-store.ts`, `expo-secure-store`) |
| `src/config.ts` | `API_URL`, from `EXPO_PUBLIC_API_URL` (default `http://10.0.2.2:3000`, the emulator's alias for the host) |
| `src/components/`, `src/hooks/` | Shared components and hooks |
| `scripts/` | `build-apk.mjs` and `e2e.mjs`, plus `env.mjs` which finds the Android toolchain |
| `.maestro/` | End-to-end flows (Maestro) |

## Signed-in screens and the navigation guard

Screens a Member sees only when signed in live in `app/(app)/` (the folder name is a route group: `app/(app)/home.tsx` is the route `/home`). The root `_layout.tsx` wraps the navigator in `AuthProvider` and mounts that group with `Stack.Protected guard={signedIn}`, and the welcome, sign-in, sign-up and forgot-password screens with `guard={!signedIn}`. Signing in or out flips the guard and expo-router moves the Member; a link to a protected route while signed out goes nowhere. A new Member screen is a file under `app/(app)/`, and it can call `useMember()` for the profile. An API call that needs the signed-in Member goes through `useAuth().request((accessToken) => api.something(accessToken))`, which renews the session once when the access token has expired and signs the Member out when it cannot be renewed. The session is kept in `expo-secure-store` (a native module: a rebuild of the APK is needed after adding it). If the server cannot be reached at launch with a stored session, the app shows a retry screen instead of signing the Member out.

The `android/` folder is generated by `expo prebuild` and is not committed.

## Forgot password

No Figma frames, so it is built from the screens around it. "Forgot password?" under Continue on sign-in (where the login frame has it, testID `sign-in-forgot-password`) opens `app/forgot-password/`, carrying the email typed so far:

- `index.tsx`: the email, laid out like the sign-up email step. Send code calls `POST /members/password-reset`, which answers the same for any email.
- `verify.tsx`: the sign-up code entry, now the shared `src/components/CodeEntryScreen.tsx` (sign-up's `verify.tsx` uses it too), with "Didn’t get a code? Send a new code". A correct code is checked at `/check` before the next step.
- `new-password.tsx`: `src/password/NewPasswordForm.tsx`, the Change password frames (926:14226 to 926:14542) without Current Password: New Password, Confirm New Password, the requirements (at least 8 characters, both match), Cancel and Save. It ends on `src/password/PasswordUpdatedDialog.tsx` (success frame 928:14929), whose button goes back to sign-in. Nobody is signed in by a reset.
- `src/password/PasswordField.tsx` is the 48 pt field of those frames; Change password (below) reuses it, `NewPasswordForm` and `PasswordUpdatedDialog`.
- Deliberate differences from the Change password frames: no strength meter and no "Contains a letter and a number", because neither is a sign-up rule and the API does not enforce them; "Both passwords match" is listed in their place. Montserrat throughout (the frames mix in Inter and Metropolis).

## Change password

`app/(app)/change-password.tsx`, pushed from the Change password row of My Account. It is the Change password frames (Figma 926:14226 to 926:14542, success 928:14929) on `NewPasswordForm`: a Current Password field (`leadingFields`, testID `current-password`), New Password and Confirm New Password, the requirements (at least 8 characters, both match, "Different from your current password" as an `extraRequirements` entry), Cancel and Save changes (dimmed until Current Password is filled and every requirement is met). `PUT /members/me/password` runs through `useAuth().request`. A wrong current password (`403 current_password_incorrect`) shows the frame's red Current Password state with "Current password is incorrect."; the API counts it with failed sign-ins, so a block (`429`) shows under the form like any other failure. The change ends every other session of the account and keeps this one, so the success dialog's "Back to My Account" returns to My Account with the Member still signed in.

- Deliberate differences from the frames: no strength meter and no "Contains a letter and a number" (as in Forgot password), "Both passwords match" listed in their place, the dialog button says "Back to My Account", the bottom navbar is not built. Current Password uses the 12 pt label and 13 pt text of the other fields: the frames disagree (926:14226 draws it at 14 pt, 926:14476 and 926:14542 at 12 and 13), and two of three agree with the other fields.

## Home and catalog search

`app/(app)/home.tsx` is Home (Figma "Home dashboard", node 1032:1994): the greeting, the search bar, and under it the search results. The recommendation sections, the bell, the menu and the bottom nav are not built; Loans and Holds and the Digital ID come with their tickets. `src/catalog/useCatalogSearch.ts` runs the search as the Member types (300 ms pause, stale answers dropped) through `useAuth().request`, and has five states: idle, loading, results, empty (neutral "No books found") and error ("Search is not working" with Try again). The pieces are in `src/home/`. Each result shows its available Copy count from the API.

## Profile and My Account

Both Profile frames of the design are built, cut down to what exists.

- **Profile** (`app/(app)/profile.tsx`, Figma node 572:1468) opens from the avatar and greeting in the Home header (testID `home-profile`). It shows the Member avatar, name, email and Account Type (in the place of the design's ID number line), a menu with one row, **My account**, and **Sign out, which lives only here**. Saved books, Borrowing history, Fines, Help and the barcode panel are not built. The Clearance status (ticket #38) goes in the menu where the design has its Fines row.
- **My Account** (`app/(app)/my-account.tsx`, node 580:1742) opens from the My account row. It shows the avatar and read-only Full name, Email and Account Type fields, all from the `GET /members/me` profile the app already holds. Edit Photo, editing with Cancel and Save changes, Student ID and Google account are not built. The **Change password** row under the fields (`MenuRow` with `variant="action"`, Figma 580:1832) opens the Change password screen.
- `src/account/` holds the pieces they share (`BackButton`, `MenuRow`, `ReadOnlyField`), `src/components/Avatar.tsx` the round avatar (also on Home), `src/hooks/useGoBack.ts` the back action every pushed screen uses, and `memberFullName` in `@libras/shared` writes the name.
- Deliberate differences from the frames: the button says "Sign out", not "Log out"; the rows and buttons use the symmetric `spacing.screen` margin, not the frame's 30 and 26; fields use `colors.surface`, the fill of the app's text fields.

## The Book page

Tapping a search result opens `app/(app)/book/[id].tsx`: the Figma "Book detail" sheet (node 609:1066) over Home, shown as a transparent modal (`presentation: "transparentModal"` in `app/(app)/_layout.tsx`). `src/catalog/useBook.ts` fetches `GET /catalog/books/:id` and has four states: loading, loaded, missing (no such Book) and error (with Try again). `src/book/BookInfo.tsx` draws the call number, cover, title, authors, edition, availability pill, the figures (year published, number of Copies, Copies available) and the ISBN. The design's genre tag, page count and description have no catalog field, and Save comes with its ticket, so they are not drawn. A Visitor or Alumni sees a "cannot borrow" note (`canBorrow` from `@libras/shared`). The Book page uses IBM Plex Mono and Roboto Mono for the call number, as the design does, and Montserrat ExtraLight for the author.

## Holds

A Member who can borrow (`canBorrow`) sees a Hold action at the foot of the Book page when the Book has no available Copy (`src/holds/HoldAction.tsx`): "Place a Hold" calls `POST /holds`, and once placed the panel says "You have a Hold on this Book: waiting" with a way to the Holds screen. A Book with an available Copy has no Hold action, and a Visitor or Alumni sees only the cannot-borrow note. A refusal from the API (`hold_exists`, `copy_available`, `book_on_loan`) is shown in the panel as the API words it.

`app/(app)/holds.tsx` is the Holds screen: the Member's Holds in two groups, Active (waiting, ready for pickup) and Past (borrowed, expired, cancelled), each with a status pill and the day it was placed in the library's time ("Placed Nov 11, 2026", `formatLibraryDate`), whatever the phone's time zone. A ready Hold has a green panel: "A Copy is set aside for you" and the end of the Pickup Window in the library's time (`formatLibraryDateTime` in `@libras/shared`, "Nov 14, 2026, 10:00 AM"). A waiting or ready Hold has "Cancel Hold", which asks once ("Leave the queue for this Book?", or for a ready Hold "Give up the Copy that is set aside for you?") before it calls `POST /holds/:id/cancel`. On the Book page a ready Hold's panel says until when the Copy is set aside and has "Show my Digital ID"; once the Librarian lends the Copy, the Digital ID screen gives way to Successfully Borrowed as for any Loan, and the Hold is listed under Past as Borrowed. Home shows a summary card ("1 waiting, 1 ready for pickup", "No active Holds") that opens the screen (`src/holds/HoldsSummary.tsx`). There is no Figma frame for these: they use the Home and Book page tokens and panels. `src/holds/useHolds.ts` fetches the Holds whenever its screen comes into focus, so Home reflects a Hold placed or cancelled elsewhere.

## Loans

A Member who can borrow sees Borrow at the foot of the Book page when the Book has an available Copy (`src/loans/BorrowAction.tsx`, Figma 609:1066). Borrow records nothing: it opens the Digital ID. A Member at their loan limit is told so instead. While the Digital ID is open, `useNewLoan` (`src/loans/useLoans.ts`) asks the API for the Member's Loans every 2.5 s; the first current Loan that was not there when the screen opened is the one the Librarian has just confirmed, and the screen gives way to `app/(app)/borrowed.tsx`, "Successfully Borrowed" (Figma 617:3485): the Book, the checkout and due dates, the days left and the Member's Loans against their limit, with Home and View My Books. The design's "to avoid a fine" is left out, because Tier 1 charges nothing.

`app/(app)/loans.tsx` is My Loans: Current (each Loan with "Borrowed on" and "Return by", an "On loan" pill, and for an overdue one a red "Overdue" pill, "Was due" in red and a notice at the top) and Past Loans (Loans the Librarian has recorded as returned: "Borrowed on", "Returned on" and a muted "Returned" pill, the latest return first). When nothing is out but some Loans are past, a "No current Loans" panel sits above them. A return needs no action in the app: the Loan moves from Current to Past Loans the next time the screen loads, and Home's summary stops counting it. Home shows a summary card ("2 current Loans, 1 overdue", "No current Loans") that opens it (`src/loans/LoansSummary.tsx`). There is no Figma frame for My Loans or the card: they use the Home, Book page and Holds tokens.

**Renewals.** Each current Loan row (`src/loans/LoanRow.tsx`) shows what the API's `renewal` says: a Renew button when the Loan can be renewed, or in its place the reason it cannot (`RENEWAL_REASONS` in `@libras/shared`: overdue, already renewed, another Member waiting). Renew asks once more inline, in the style of Cancel Hold, with the new due date the API gave and, when this Renewal uses up the renewal limit, that it cannot be renewed again. After the Renewal the list reloads: the row has the new "Return by" date and a "Renewed" pill. When the API refuses (something changed since the list loaded), the row shows the API's message and the list reloads, so the fresh reason replaces the button. The app holds no Renewal rules of its own. Dates are days of the library's calendar (`formatLibraryDate` in `@libras/shared`), whatever the phone's time zone, and overdue is the API's word, not the phone's clock.

## One-time setup (Windows, user space)

- Node 24, Android Studio (for its JDK and the emulator) and an AVD (`Medium_Phone` by default; override with `LIBRAS_AVD`). `npm run e2e` stops at once, listing the AVDs it found, when `LIBRAS_AVD` names none of them. `Medium_Phone` is the AVD the flows are known to pass on.
- Android SDK packages: `platforms;android-37.0`, `build-tools;37.0.0`, `ndk;27.1.12297006` and the command-line tools (`cmdline-tools;latest`). Install them with `sdkmanager`.
- Maestro, the end-to-end runner, unzipped to `~/tools/maestro` (or point `MAESTRO_HOME` at it): https://github.com/mobile-dev-inc/maestro/releases/latest/download/maestro.zip

`scripts/env.mjs` finds `JAVA_HOME` (Android Studio's `jbr`), `ANDROID_HOME`, Maestro and `adb` on its own. Set `JAVA_HOME`, `ANDROID_HOME` or `MAESTRO_HOME` to override.

## Run the app

From the repo root:

```bash
npm run dev                                  # local Supabase and the API on :3000
npm run build:apk -w @libras/mobile          # release APK -> apps/mobile/build/libras.apk
adb install -r apps/mobile/build/libras.apk  # onto a running emulator or a device
```

The app is a release build with its JavaScript bundled in, so there is no live reload: rebuild the APK after a change. Expo Go is not used (see Expo limitations below).

After one full build, a change to JavaScript only needs Gradle again, without `expo prebuild --clean` (which throws the native build away): from `apps/mobile/android` run `gradlew.bat assembleRelease -I ../scripts/short-native-build.init.gradle --no-daemon` with `JAVA_HOME`, `ANDROID_HOME`, `LIBRAS_NATIVE_BUILD_DIR=C:/lb` and `LIBRAS_CMAKE_VERSION=3.31.6` set (see `scripts/build-apk.mjs`), then copy `android/app/build/outputs/apk/release/app-release.apk` to `build/libras.apk`. That took about 2.5 minutes instead of 27. A reinstall of `node_modules` makes Gradle redo the native part once.

`EXPO_PUBLIC_API_URL` is baked in at build time. A build whose URL starts with `http://` (or is unset) allows cleartext traffic; an `https://` build does not. For a phone on the same network, set it to `http://<your-computer-LAN-ip>:3000` and rebuild.

To build against the hosted API on Render, run `npm run build:apk:hosted -w @libras/mobile`. It takes `EXPO_PUBLIC_API_URL` from its first argument, the environment or `.env.hosted` (written by `npm run setup:hosted`), refuses anything that is not `https://`, and asks the API for `/health` before the long build starts (a sleeping free Render service takes about a minute to answer). It reads only that one value from `.env.hosted`. The build is about 25 minutes, so it is not run casually. See the Deployment section of the root README.

`LIBRAS_ABIS` (default `arm64-v8a,x86,x86_64`) sets the CPU architectures in the APK. Use `x86_64` alone for a faster emulator-only build. `npm run e2e` stops before installing an APK that has none of the device's architectures.

## End-to-end test

Seventeen flows run: the smoke test (the `libras://status` screen shows the health result), `sign-up-umak-student.yaml`, which signs a student up through the real screens and reads the verification code from the emails the end-to-end API captured (see `apps/api/README.md`), `sign-up-faculty.yaml`, `sign-up-ntp-employee.yaml`, `sign-up-visitor.yaml` and `sign-up-alumni.yaml` (the same for the other Account Types, sharing the steps in `.maestro/subflows/`), `sign-in.yaml` (sign in, stay signed in across a restart, sign out from the profile, protected screen unreachable, wrong credentials, a forgotten password reset with the emailed code and then signing in with the new one, unverified account), `search.yaml` (signs a Member in and searches Books that `scripts/create-books.js` adds through the end-to-end API), `book.yaml` (opens a Book from the results as a UMAK Student and as a Visitor, and checks the details, the Copy counts and the cannot-borrow note), `holds.yaml` (a UMAK Student places a Hold on a Book with no available Copy, sees it on Home and on the Holds screen and cancels it; a Book with a Copy has no Hold action and a Visitor is not offered one), `hold-ready.yaml` (a UMAK Student places a Hold on a Book whose only Copy is out with another Member; the end-to-end API records the return as the desk page would, and the script checks the desk's answer and the Hold-ready email; the app shows the Hold as ready with the end of the Pickup Window on the Holds screen, on Home and on the Book page; the Librarian then lends the set-aside Copy and the Hold is listed as borrowed), `hold-expired.yaml` (the same until the Hold is ready, then the Pickup Window runs out: the end-to-end API runs the expiry sweep with nobody opening the app, and the app shows the Hold as Expired on the Holds screen, Home counts no active Hold, and the Book is available again), `loans.yaml` (Borrow opens the Digital ID and records nothing; the end-to-end API then confirms the Loan as a Librarian would, with the code on the Member's phone, and the app shows Successfully Borrowed, My Loans and the Home summary; the Member renews the Loan through the confirmation and sees the new due date and the Renewed pill; then an overdue Loan and a Loan of a Book another Member places a Hold on while My Loans is open (`scripts/wanted-loan.js`, `hold-on-wanted-loan.js`), whose Renewal is refused with the reason), `returns.yaml` (a Copy is out; the end-to-end API records its return as the desk page would, and the Loan moves from Current to Past Loans with its return date, Home stops counting it, and the Book is available again in search and on its page), `profile.yaml` (opens Profile from the Home header, checks the name, email and Account Type, opens My Account and checks its fields, goes back, and signs out from Profile), and `digital-id.yaml` (opens the Digital ID from the home screen and waits, up to 75 s of real time, for the code to be replaced without a tap). The sign-in flow makes its Members through the API with `scripts/create-member.js`. The end-to-end API raises the sign-in and Forgot password limits so repeated runs from one address are not blocked.

```bash
npm run db:start
npm run build:apk -w @libras/mobile
npm run e2e -w @libras/mobile
```

`npm run e2e` starts the end-to-end API (the one that captures emails; it refuses to run if another API already holds port 3000), starts the emulator if no device is connected, installs `build/libras.apk` and runs every flow in `.maestro/` with Maestro. It stops what it started. It is not part of `npm test` because it needs an emulator.

Checks that need no emulator: `npm run typecheck` and `npm run lint` from the repo root.

## Expo limitations that affect Tier 1

- **Builds.** Builds are local (`expo prebuild` plus Gradle); no EAS account is needed. The first build downloads Gradle and takes about 10 minutes, later ones less. React Native 0.88 needs compileSdk 37, build-tools 37.0.0 and NDK 27.1. The release APK is signed with the Expo template's debug keystore: fine for the demo, not for a store. There is no live reload against a release APK (rebuild instead); a development client (`expo-dev-client`) would be needed for that. On Windows a long repository path breaks the native CMake step, which is why `build-apk.mjs` builds from a `subst` drive.
- **Cleartext HTTP.** Android blocks `http://` by default. `app.config.ts` allows it only when `EXPO_PUBLIC_API_URL` is `http://` or unset (local use). A build against the HTTPS API on Render needs no exception.
- **Camera.** Tier 1 scanning runs on the Librarian phone scanner web page in the phone's browser, so the app needs no camera. If the app ever needs one, `expo-camera` supports barcode scanning, but camera behaviour cannot be automated on the emulator: it needs a manual check on a real device.
- **Barcode rendering.** Expo ships no 1D barcode renderer. The Digital ID is encoded as Code 128 subset C by `encodeCode128C` in `@libras/shared` and drawn with `react-native-svg` by `src/digital-id/Barcode.tsx`, each module a whole number of physical pixels.
- **Native modules.** Anything beyond the Expo SDK (a library with its own native code) is compiled into the APK by prebuild's autolinking, so it works, but a JS-only change is not enough: rebuild the APK.
- **Secure storage and push.** `expo-secure-store` works in the APK for the signed-in session. Push notifications are out of scope for Tier 1.
- **Shared code.** `@libras/shared` is imported as TypeScript source and bundled by Metro. Its relative imports end in `.ts`, which Metro and `tsc` here both accept.
