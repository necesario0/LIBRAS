# @libras/mobile

The Member mobile app: React Native with TypeScript, built with Expo SDK 58 (React Native 0.88, new architecture) and Expo Router, targeting an Android APK (ADR 0002). It talks only to the API (`apps/api`) and takes shared types from `@libras/shared`.

Today it has the welcome screen and the sign-up flow for all five Account Types (account type, name, the details that Account Type gives, username and password, email, emailed code, welcome). The details step is `student.tsx`, `faculty.tsx`, `ntp-employee.tsx`, `visitor.tsx` or `alumni.tsx` in `app/sign-up/`; `src/sign-up/request.ts` maps the Account Type to its step and builds its request. Faculty, NTP / Employee and UMAK Student share `src/sign-up/CollegeIdStep.tsx`. Faculty and NTP / Employee need an `@umak.edu.ph` email; Visitor and Alumni accept any. `libras://status` opens the developer screen that calls `GET /health`.

## Layout

| Path | What |
| --- | --- |
| `app/` | Expo Router screens: one file is one route. `_layout.tsx` loads Montserrat and holds the navigation stack |
| `src/theme/tokens.ts` | Color, type, spacing and radius tokens, defined once from the Figma frames |
| `src/api/client.ts` | The API client: every endpoint is a method, every failure is an `ApiError` |
| `src/auth/` | The Member's session: `AuthProvider` and `useAuth()` (`AuthContext.tsx`), the logic that renews it (`SessionManager.ts`) and where it is kept (`session-store.ts`, `expo-secure-store`) |
| `src/config.ts` | `API_URL`, from `EXPO_PUBLIC_API_URL` (default `http://10.0.2.2:3000`, the emulator's alias for the host) |
| `src/components/`, `src/hooks/` | Shared components and hooks |
| `scripts/` | `build-apk.mjs` and `e2e.mjs`, plus `env.mjs` which finds the Android toolchain |
| `.maestro/` | End-to-end flows (Maestro) |

## Signed-in screens and the navigation guard

Screens a Member sees only when signed in live in `app/(app)/` (the folder name is a route group: `app/(app)/(tabs)/home.tsx` is the route `/home`). The root `_layout.tsx` wraps the navigator in `AuthProvider` and mounts that group with `Stack.Protected guard={signedIn}`, and the welcome, sign-in, sign-up and forgot-password screens with `guard={!signedIn}`. Signing in or out flips the guard and expo-router moves the Member; a link to a protected route while signed out goes nowhere. A new Member screen is a file under `app/(app)/`, and it can call `useMember()` for the profile. An API call that needs the signed-in Member goes through `useAuth().request((accessToken) => api.something(accessToken))`, which renews the session once when the access token has expired and signs the Member out when it cannot be renewed. The session is kept in `expo-secure-store` (a native module: a rebuild of the APK is needed after adding it). If the server cannot be reached at launch with a stored session, the app shows a retry screen instead of signing the Member out.

## Tabs and pushed screens

The signed-in app is a stack (`app/(app)/_layout.tsx`) with the tabs at the bottom and every other screen pushed over them:

- **Tabs** (`app/(app)/(tabs)/_layout.tsx`, expo-router's JavaScript `Tabs`): Home, My Books, Digital ID and Profile, under the floating tab bar `src/navigation/FloatingTabBar.tsx` (the approved Tier 3 preview: a white 70 pt pill 14 pt in from the sides, the active tab in blue). There is no drawer and no burger. Android's back button on another tab returns to Home (`backBehavior="firstRoute"`). A tab screen leaves `useTabBarSpace()` of room under its content, and can hide the bar with `useHideTabBar(true)` (`src/navigation/TabBarVisibility.tsx`, for example Home's search mode); the bar also steps aside while the keyboard is up. A tab's label, icon (`src/components/OutlineIcons.tsx`) and test id (`tab-home`, `tab-my-books`, `tab-digital-id`, `tab-profile`) are its `Tabs.Screen` options; a `tabBarBadge` shows as a red dot (`tab-my-books-dot`).
- **Pushed screens** (My Account, Change password, Successfully Borrowed, and the Book page sheet) are siblings of `(tabs)` in `app/(app)/`, so they cover the tab bar. Each has its back button at the top left, before the title (`src/navigation/PushedHeader.tsx`), and Android's back button does the same. `unstable_settings.initialRouteName = "(tabs)"` keeps the tabs under a pushed screen opened by a link.
- To switch tab from a pushed screen, use `router.dismissTo("/digital-id")` (or `{ pathname: "/my-books", params: { segment: "holds" } }`): it closes the pushed screens and selects the tab. Inside the tabs, `router.navigate("/profile")` is enough.
- **My Books data.** `MyBooksProvider` (`src/my-books/MyBooksContext.tsx`, mounted by the tabs layout) holds the Member's Loans and Holds for all the tabs, fetched again whenever a tab comes into focus and when the app returns to the foreground. `useMyBooks()` gives the Loans, the Holds, `canBorrow` (the Loan Policy's loan limit is above zero, from `GET /members/me/loans`; undefined until loaded) and `attention` (`myBooksAttention` in `@libras/shared`: a ready Hold, or a current Loan due tomorrow by the library's calendar or overdue). The My Books tab is labelled "Saved" with a bookmark when `canBorrow` is false, and has a dot when either part of `attention` is true. Nothing else earns a dot.

The `android/` folder is generated by `expo prebuild` and is not committed.

## Forgot password

No Figma frames, so it is built from the screens around it. "Forgot password?" under Continue on sign-in (where the login frame has it, testID `sign-in-forgot-password`) opens `app/forgot-password/`, carrying the email typed so far:

- `verify.tsx`: the sign-up code entry, now the shared `src/components/CodeEntryScreen.tsx` (sign-up's `verify.tsx` uses it too), with "Didn’t get a code? Send a new code". A correct code is checked at `/check` before the next step.
- `new-password.tsx`: `src/password/NewPasswordForm.tsx`, the Change password frames (926:14226 to 926:14542) without Current Password: New Password, Confirm New Password, the requirements (at least 8 characters, both match), Cancel and Save. It ends on `src/password/PasswordUpdatedDialog.tsx` (success frame 928:14929), whose button goes back to sign-in. Nobody is signed in by a reset.
- `src/password/PasswordField.tsx` is the 48 pt field of those frames; Change password (below) reuses it, `NewPasswordForm` and `PasswordUpdatedDialog`.
- Deliberate differences from the Change password frames: no strength meter and no "Contains a letter and a number", because neither is a sign-up rule and the API does not enforce them; "Both passwords match" is listed in their place. Montserrat throughout (the frames mix in Inter and Metropolis).

## Change password

`app/(app)/change-password.tsx`, pushed from the Change password row of Profile. It is the Change password frames (Figma 926:14226 to 926:14542, success 928:14929) on `NewPasswordForm`: a Current Password field (`leadingFields`, testID `current-password`), New Password and Confirm New Password, the requirements (at least 8 characters, both match, "Different from your current password" as an `extraRequirements` entry), Cancel and Save changes (dimmed until Current Password is filled and every requirement is met). `PUT /members/me/password` runs through `useAuth().request`. A wrong current password (`403 current_password_incorrect`) shows the frame's red Current Password state with "Current password is incorrect."; the API counts it with failed sign-ins, so a block (`429`) shows under the form like any other failure. The change ends every other session of the account and keeps this one, so the success dialog's "Back to Profile" returns to Profile with the Member still signed in.

- Deliberate differences from the frames: no strength meter and no "Contains a letter and a number" (as in Forgot password), "Both passwords match" listed in their place, the dialog button says "Back to Profile", the screen is pushed over the tabs so the tab bar is hidden. Current Password uses the 12 pt label and 13 pt text of the other fields: the frames disagree (926:14226 draws it at 14 pt, 926:14476 and 926:14542 at 12 and 13), and two of three agree with the other fields.

## Home and catalog search

`app/(app)/(tabs)/home.tsx` is the Home tab (Figma "Home dashboard", node 1032:1994, laid out as the approved Tier 3 preview): the avatar and greeting ("Hi, <first name>", then "What’s on your mind"), which open the Profile tab, the bell at the right (see Notifications below), the search bar, and under it the search results. There is no menu, and Loans, Holds and the Digital ID have their own tabs. The shelves come with their ticket. `src/catalog/useCatalogSearch.ts` runs the search as the Member types (300 ms pause, stale answers dropped) through `useAuth().request`, and has five states: idle, loading, results, empty (neutral "No books found") and error ("Search is not working" with Try again). The pieces are in `src/home/`. Each result shows its available Copy count from the API.

## Profile and My Account

Both Profile frames of the design are built, cut down to what exists.

- **Profile** (`app/(app)/(tabs)/profile.tsx`, Figma node 572:1468, laid out as the approved Tier 3 preview) is a tab, and also opens from the avatar and greeting in the Home header (testID `home-profile`). It shows the Member avatar, name, email and Account Type (in the place of the design's ID number line), the rows **My account**, **Clearance** and **Change password** (`MenuRow` with an outline icon), and **Sign out, which lives only here**. **Settings** and **Help and policies** follow Change password (see Settings and Help below). The **Clearance** panel (`src/clearance/ClearancePanel.tsx`, data from `useClearance`, `GET /members/me/clearance`): the Fines row's white pill with the dollar sign (Figma 921:14028), a Cleared or Not cleared pill where the design has the chevron, and, when not cleared, the Loans still out and the unsettled Fines (with `formatPesos` amounts) inside the same card. A Member who is not in Good standing reads first, in a red note inside the card (`profile-good-standing`, `goodStandingNotice`), that they cannot borrow, place a Hold or renew, why, and what to do at the desk. It refetches whenever Profile comes into focus. The app holds no Clearance or Good standing rule.
- **My Account** (`app/(app)/my-account.tsx`, node 580:1742) is pushed from the My account row, with back at the top left (`PushedHeader`). It shows the avatar and read-only Full name, Email and Account Type fields, all from the `GET /members/me` profile the app already holds. Edit Photo, editing with Cancel and Save changes, Student ID and Google account are not built. Change password is a Profile row.
- `src/account/` holds the pieces they share (`BackButton`, `MenuRow`, `ReadOnlyField`), `src/components/Avatar.tsx` the round avatar (also on Home), `src/hooks/useGoBack.ts` the back action every pushed screen uses, and `memberFullName` in `@libras/shared` writes the name.
- Deliberate differences from the frames: the button says "Sign out", not "Log out"; the rows and buttons use the symmetric `spacing.screen` margin, not the frame's 30 and 26; fields use `colors.surface`, the fill of the app's text fields.

## Settings and Help and policies

Pushed screens in `app/(app)/`, built from `src/settings/SettingsParts.tsx` (`SectionLabel`, `SettingsGroup`, `SettingsRow`, `SettingsSwitchRow`, `SettingsNote`, `FactTable`) as the approved Tier 3 preview.

- `settings.tsx`: Push notifications first (`src/settings/PushNotifications.tsx`: four switches read with `GET /members/me/push-settings` and saved one by one with `PATCH`, moving at once and back with a toast if the save fails; a note with a way to the phone's settings when Android blocks LIBRAS notifications; the line that Loan notice emails are always sent), then Privacy and security (Clear search history: `clearRecentSearches()`, a short toast, the row's count of recent searches on this phone; Sign out of all devices: `ConfirmDialog`, then `POST /members/me/sign-out-all` and a local `signOut()`, which returns to sign-in), Library (Library info), Account (Delete my account: `src/settings/DeleteAccount.tsx` reads the Clearance first; not cleared shows `notClearedNotice` with Close and See My Loans, or See Clearance when only Fines are left; cleared asks for the password in a `ConfirmDialog` of `tone="danger"`, then `POST /members/me/delete` and a local `signOut()`) and the version from `expo-constants`.
- `help.tsx`: `useLoanPolicy` (`GET /members/me/loan-policy`) and `loanPolicyHelp` (shared) word the Member's own Loan Policy; an Account Type that cannot borrow is told so. Terms and Conditions and Privacy Policy both open `/terms`, which holds both texts.
- `library-info.tsx`: static text from `src/settings/library-info.ts`. Every value is an example marked `toConfirm` until the library supplies the real ones; the screen says so.
- Flows: `settings.yaml`, `settings-push.yaml` and `help-policies.yaml`.

## Push notifications

`src/push/`. `push-device.ts` knows whether this build can get push notifications (`app.config.ts` sets `extra.pushEnabled` only with `google-services.json` and `EXPO_PROJECT_ID`; `LIBRAS_PUSH=off` forces it off) and gets the phone's Expo push token, asking Android's permission once. `usePushNotifications` (mounted in `app/(app)/_layout.tsx`) registers the phone with `PUT /members/me/push-device` on every start and opens the screen of a tapped push (`pushDestination` in `@libras/shared`: My Books on Holds or Loans, or `/announcement`). Sign-out hands the token back in `POST /auth/sign-out`, also when the session ended on its own. A build without push notifications skips all of it and never shows the permission dialog. The owner's Firebase and Expo setup: `docs/push-notifications.md`.

## Notifications

The notification inbox works on every build, with or without push notifications: it only talks to the API.

- **The bell** (`src/home/NotificationBell.tsx`, testID `home-bell`) sits at the right of the Home header. Its red badge (`home-bell-badge`) counts the unread Notifications (`unreadBadgeText` in `@libras/shared`: none at zero, "9+" above nine). `useUnreadNotifications` reads `GET /members/me/notifications/unread` whenever Home comes into view and whenever the app returns to the foreground while Home shows. There is no polling.
- **The Notifications screen** (`app/(app)/notifications.tsx`, pushed): back at the top left and Mark all as read at the right (`PushedHeader`'s `action`, which moves under the title when large text leaves no room beside it), then the list (`src/notifications/NotificationRow.tsx`): the kind's icon in a ring, the title, how long ago (`notificationAge`), the line, and a blue dot while unread (`notification-unread`). Rows have the testID `notification-<kind>`. More pages load as the list reaches its end. Tapping a row marks it read (`POST .../:id/read`) and opens the screen its push notification opens (`notificationDestination`): My Books on Holds or Loans (`router.dismissTo`), or the Announcement (pushed, so back returns to the list). Mark all as read calls `POST .../read-all`. With no Notification, one line says what will show there (`notifications-empty`).
- Flows: `notifications.yaml` (with `scripts/create-notifications.js`) and `notifications-empty.yaml`.

## The Book page

Tapping a search result opens `app/(app)/book/[id].tsx`: the Figma "Book detail" sheet (node 609:1066) over Home, shown as a transparent modal (`presentation: "transparentModal"` in `app/(app)/_layout.tsx`). `src/catalog/useBook.ts` fetches `GET /catalog/books/:id` and has four states: loading, loaded, missing (no such Book) and error (with Try again). `src/book/BookInfo.tsx` draws the call number, cover, title, authors, edition, availability pill, the figures (year published, number of Copies, Copies available) and the ISBN. The design's genre tag, page count and description have no catalog field, and Save comes with its ticket, so they are not drawn. A Visitor or Alumni sees a "cannot borrow" note (`canBorrow` from `@libras/shared`). The Book page uses IBM Plex Mono and Roboto Mono for the call number, as the design does, and Montserrat ExtraLight for the author.

## Holds

A Member who can borrow (`canBorrow`) sees a Hold action at the foot of the Book page when the Book has no available Copy (`src/holds/HoldAction.tsx`): "Place a Hold" calls `POST /holds`, and once placed the panel says "You have a Hold on this Book: waiting" with a way to the Holds segment of My Books. A Book with an available Copy has no Hold action, and a Visitor or Alumni sees only the cannot-borrow note. A refusal from the API (`hold_exists`, `copy_available`, `book_on_loan`, `overdue_loan`, `unsettled_fine`) is shown in the panel as the API words it. The Book page also reads the Member's Good standing (`useClearance`, `GET /members/me/clearance`): when not in it, the Hold panel (`hold-not-in-good-standing`) and Borrow (`borrow-not-in-good-standing`) both show the Profile's note in place of their button (`goodStandingNotice`).

The Holds segment of the My Books tab (`app/(app)/(tabs)/my-books.tsx`, `src/my-books/HoldsSegment.tsx`) lists the Member's Holds in two groups, Active (waiting, ready for pickup) and Past (borrowed, expired, cancelled), each with a status pill and the day it was placed in the library's time ("Placed Nov 11, 2026", `formatLibraryDate`), whatever the phone's time zone. A ready Hold has a green panel: "A Copy is set aside for you" and the end of the Pickup Window in the library's time (`formatLibraryDateTime` in `@libras/shared`, "Nov 14, 2026, 10:00 AM"). A ready Hold also has "Show my Digital ID", which opens the Digital ID tab. A waiting or ready Hold has "Cancel Hold", which asks once ("Leave the queue for this Book?", or for a ready Hold "Give up the Copy that is set aside for you?") before it calls `POST /holds/:id/cancel`. On the Book page a ready Hold's panel says until when the Copy is set aside and has "Show my Digital ID"; once the Librarian lends the Copy, the Digital ID screen gives way to Successfully Borrowed as for any Loan, and the Hold is listed under Past as Borrowed. "See my Holds" on the Book page opens the Holds segment. A ready Hold puts a dot on the My Books tab and on the Holds segment, and My Books opens on Holds while one is ready. There is no Figma frame for these: they use the Home and Book page tokens and panels.

## My Books

`app/(app)/(tabs)/my-books.tsx` is the My Books tab (approved Tier 3 preview): the title, then the segment control (`src/my-books/SegmentControl.tsx`, `my-books-loans` and `my-books-holds`, each with a dot when it needs the Member) over the Loans or Holds segment. Each time the tab comes into focus it fetches again and opens on Holds when a Hold is ready, otherwise on Loans (`myBooksStartSegment`), and keeps that segment until the Member picks another or leaves the tab. `/my-books?segment=loans` (or `holds`) opens it on that segment once. A Member who cannot borrow sees "Saved books" with a placeholder (`saved-placeholder`) and no segments, until the Saved books ticket fills it; that ticket also adds a Saved segment: one more entry in the `segments` list and one more branch in the screen.

## Digital ID

`app/(app)/(tabs)/digital-id.tsx` is the Digital ID tab (Figma 617:3265, laid out as the approved Tier 3 preview): the barcode and its code, "New code in m:ss", the Member's name and Account Type, and a note that the screen is kept bright. Its content is mounted only while the tab is in focus, so the code is fetched, the screen lit (`src/digital-id/useBrightScreen.ts`: `expo-keep-awake` and `expo-brightness`, this app's window only, no permission) and the desk watched for a new Loan (which opens Successfully Borrowed over it) only then. Leaving the tab, opening a screen over it, or the app going to the background gives the phone its brightness and screen timeout back. Both are native modules: a full APK build is needed after adding them.

## Loans

A Member who can borrow sees Borrow at the desk at the foot of the Book page when the Book has an available Copy (`src/loans/BorrowAction.tsx`, Figma 609:1066). It records nothing: it opens the Borrow sheet over the Book (`src/loans/BorrowSheet.tsx`), with two steps, "Take it from the shelf" and the Book's call number (`src/book/CallNumber.tsx`), then "Show this code to the librarian" and the live Digital ID (`src/digital-id/DigitalIdTicket.tsx`, the same card as the Digital ID tab), at full brightness while it is open. "Open my Digital ID" closes the sheet and the Book page and opens the tab. A Member at their loan limit is told so instead, and a Member who is not in Good standing reads the red `StandingNotice` (`src/standing/StandingNotice.tsx`), which also shows on Home, in place of Place a Hold and on the Digital ID tab, with a way to the Loans or to Clearance. While the Borrow sheet is open or the Digital ID tab is in focus, `useNewLoan` (`src/loans/useLoans.ts`) asks the API for the Member's Loans every 2.5 s; the first current Loan that was not there when the screen opened is the one the Librarian has just confirmed, and the screen gives way to `app/(app)/borrowed.tsx`, "Successfully Borrowed" (Figma 617:3485): the Book, the checkout and due dates, the days left and the Member's Loans against their limit, with Home and View My Books, and "Please return it by <day> to avoid a fine."

The Loans segment of the My Books tab (`src/my-books/LoansSegment.tsx`, the former My Loans screen) lists Current (each Loan with "Borrowed on" and "Return by", an "On loan" pill, and for an overdue one a red "Overdue" pill, "Was due" in red, "Fine so far: PHP 15 (3 days late)" in red from the Loan's `fine` (the API computes it; the app never does) and a notice at the top) and Past Loans (Loans the Librarian has recorded as returned: "Borrowed on", "Returned on" and a muted "Returned" pill, the latest return first). When nothing is out but some Loans are past, a "No current Loans" panel sits above them. A return needs no action in the app: the Loan moves from Current to Past Loans the next time the tab loads. A Loan due tomorrow or overdue puts a dot on the My Books tab and on the Loans segment. There is no Figma frame for the Loans list: it uses the Home, Book page and Holds tokens.

**Renewals.** Each current Loan row (`src/loans/LoanRow.tsx`) shows what the API's `renewal` says: a Renew button when the Loan can be renewed, or in its place the reason it cannot (`RENEWAL_REASONS` in `@libras/shared`: overdue, already renewed, another Member waiting, another Loan overdue, an unsettled Fine). Renew asks once more inline, in the style of Cancel Hold, with the new due date the API gave and, when this Renewal uses up the renewal limit, that it cannot be renewed again. After the Renewal the list reloads: the row has the new "Return by" date and a "Renewed" pill. When the API refuses (something changed since the list loaded), the row shows the API's message and the list reloads, so the fresh reason replaces the button. The app holds no Renewal rules of its own. Dates are days of the library's calendar (`formatLibraryDate` in `@libras/shared`), whatever the phone's time zone, and overdue is the API's word, not the phone's clock.

## One-time setup (Windows, user space)

- Node 24, Android Studio (for its JDK and the emulator) and an AVD (`Medium_Phone` by default; override with `LIBRAS_AVD`). `npm run e2e` stops at once, listing the AVDs it found, when `LIBRAS_AVD` names none of them. `Medium_Phone` is the AVD the flows are known to pass on.
- Android SDK packages: `platforms;android-37.0`, `build-tools;37.0.0`, `ndk;27.1.12297006` and the command-line tools (`cmdline-tools;latest`). Install them with `sdkmanager`.
- Maestro, the end-to-end runner, unzipped to `~/tools/maestro` (or point `MAESTRO_HOME` at it): https://github.com/mobile-dev-inc/maestro/releases/latest/download/maestro.zip

`scripts/env.mjs` finds `JAVA_HOME` (Android Studio's `jbr`), `ANDROID_HOME`, Maestro and `adb` on its own. Set `JAVA_HOME`, `ANDROID_HOME` or `MAESTRO_HOME` to override.

## Run the app

From the repo root:

```bash
npm run dev                                  # local Supabase and the API on :3000
npm run build:apk -w @libras/mobile          # release APK -> apps/mobile/build/libras.apk
adb install -r apps/mobile/build/libras.apk  # onto a running emulator or a device
```

The app is a release build with its JavaScript bundled in, so there is no live reload: rebuild the APK after a change. Expo Go is not used (see Expo limitations below).

After one full build, a change to JavaScript only needs Gradle again, without `expo prebuild --clean` (which throws the native build away): from `apps/mobile/android` run `gradlew.bat assembleRelease -I ../scripts/short-native-build.init.gradle --no-daemon` with `JAVA_HOME`, `ANDROID_HOME`, `LIBRAS_NATIVE_BUILD_DIR=C:/lb` and `LIBRAS_CMAKE_VERSION=3.31.6` set (see `scripts/build-apk.mjs`), then copy `android/app/build/outputs/apk/release/app-release.apk` to `build/libras.apk`. That took about 2.5 minutes instead of 27. A reinstall of `node_modules` makes Gradle redo the native part once.

`EXPO_PUBLIC_API_URL` is baked in at build time. A build whose URL starts with `http://` (or is unset) allows cleartext traffic; an `https://` build does not. For a phone on the same network, set it to `http://<your-computer-LAN-ip>:3000` and rebuild.

To build against the hosted API on Render, run `npm run build:apk:hosted -w @libras/mobile`. It takes `EXPO_PUBLIC_API_URL` from its first argument, the environment or `.env.hosted` (written by `npm run setup:hosted`), refuses anything that is not `https://`, and asks the API for `/health` before the long build starts (a sleeping free Render service takes about a minute to answer). It reads only that value and `EXPO_PROJECT_ID` (push notifications, see above) from `.env.hosted`. The build is about 25 minutes, so it is not run casually. See the Deployment section of the root README.

`LIBRAS_ABIS` (default `arm64-v8a,x86,x86_64`) sets the CPU architectures in the APK. Use `x86_64` alone for a faster emulator-only build. `npm run e2e` stops before installing an APK that has none of the device's architectures.

`npm run e2e` starts the end-to-end API (the one that captures emails; it refuses to run if another API already holds port 3000), starts the emulator if no device is connected, installs `build/libras.apk` and runs every flow in `.maestro/` with Maestro. It stops what it started. It also runs `adb reverse tcp:54321 tcp:54321`: the local API gives Announcement images at the local Supabase address (`http://127.0.0.1:54321`), which the device can only reach through that forward. Run the same command when you try the app against a local API by hand. It is not part of `npm test` because it needs an emulator.

Checks that need no emulator: `npm run typecheck` and `npm run lint` from the repo root.

## Expo limitations that affect Tier 1

- **Builds.** Builds are local (`expo prebuild` plus Gradle); no EAS account is needed. The first build downloads Gradle and takes about 10 minutes, later ones less. React Native 0.88 needs compileSdk 37, build-tools 37.0.0 and NDK 27.1. The release APK is signed with the Expo template's debug keystore: fine for the demo, not for a store. There is no live reload against a release APK (rebuild instead); a development client (`expo-dev-client`) would be needed for that. On Windows a long repository path breaks the native CMake step, which is why `build-apk.mjs` builds from a `subst` drive.
- **Cleartext HTTP.** Android blocks `http://` by default. `app.config.ts` allows it only when `EXPO_PUBLIC_API_URL` is `http://` or unset (local use). A build against the HTTPS API on Render needs no exception.
- **Camera.** Tier 1 scanning runs on the Librarian phone scanner web page in the phone's browser, so the app needs no camera. If the app ever needs one, `expo-camera` supports barcode scanning, but camera behaviour cannot be automated on the emulator: it needs a manual check on a real device.
- **Barcode rendering.** Expo ships no 1D barcode renderer. The Digital ID is encoded as Code 128 subset C by `encodeCode128C` in `@libras/shared` and drawn with `react-native-svg` by `src/digital-id/Barcode.tsx`, each module a whole number of physical pixels.
- **Native modules.** Anything beyond the Expo SDK (a library with its own native code) is compiled into the APK by prebuild's autolinking, so it works, but a JS-only change is not enough: rebuild the APK.
- **Secure storage and push.** `expo-secure-store` works in the APK for the signed-in session. Push notifications are out of scope for Tier 1.
- **Shared code.** `@libras/shared` is imported as TypeScript source and bundled by Metro. Its relative imports end in `.ts`, which Metro and `tsc` here both accept.
