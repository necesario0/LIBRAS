Two computational bottlenecks

Typo-tolerant search: SQL ILIKE '%term%' is a substring match with no typo tolerance. It found only 3.7% of the words within two edits, and it still scans every row.

Hold dispatch: one returned Copy needs its top-priority waiting Member resolved instantly, with no race conditions or starvation.

Problem formulation

Two coupled optimization problems

1 · Approximate string match

Per word q: minimize dLev(q, w), d ≤ k(q) ≤ 2

A Book must match every word; rank by total edit distance

2 · Priority scheduling

Select r* = argmin (PriorityScore(ri), seqi)

where PriorityScore = ti − W(ρi); smaller means higher priority

Inputs: lexicon D with N ≥ 50,000 tokens · query Q with 1 ≤ |Q| ≤ 100 · waiting Holds R with K ≤ 5,000 per Book

Algorithm selection

Dual-engine architecture

Engine 1 · Bounded Levenshtein Trie Search

Dynamic programming over a prefix tree. Shared prefixes are evaluated once, and branch-and-bound pruning skips dead subtrees. Stored as flat typed arrays.

Engine 2 · Role-Weighted Priority Queue Dispatcher

Greedy choice on an ordered index: the first entry is always the winning Member. Implemented as an indexed PostgreSQL query.

Alternatives tested and not chosen

Search: SymSpell (318 MB), per-node-object trie (55 MB), BK-tree, bigram index, pg_trgm (17% recall), ILIKE (3.7% recall), linear scan.

Queue: 4-ary, lazy-delete and pairing heaps, sorted array, unsorted scan. Full results on slide 9.

Algorithm mechanics · dispatch

An ordered index keeps the winner first

Enqueue

INSERT into holds

O(log K)

Peek

SELECT ... ORDER BY score, seq LIMIT 1

O(log K)

Dispatch

UPDATE ... FOR UPDATE SKIP LOCKED marks the Hold ready, in the same transaction as the return

O(log K)

Worked example

Faculty arriving at t scores t − 24 h and beats a UMAK Student who arrived at t − 12 h, so the returned Copy is set aside for Faculty. With 50 concurrent clients, each of 2,000 holds was served exactly once.

Empirical selection

Why these algorithms: measured against alternatives

Search candidate (50,000 tokens, k = 2)p95 (ms)MemoryOutcome
SymSpell0.19318 MBFastest; fails memory rule
Trie, object per node2.9355 MBFails memory rule
Bigram index1.975.6 MBPasses; slower as catalog grows
Flat trie (chosen)1.934.4 MBPasses; fastest from 50,000 tokens up

Rule: exact results, at least 250 queries/s, memory within 2× the smallest passing option, then lowest p95. In repeated runs the flat trie p95 was 0.73 ms against 1.25 ms (bigram) at 50,000 tokens and 2.4 ms against 21.6 ms at 400,000.

Queue: every in-memory heap is about 50,000× inside the 10 ms limit; the PostgreSQL query (1.7 ms) was chosen for durability, atomicity with the loan record, and no queue state in the application.
